## 1. 한눈에 보기

### 1.1 서비스 정의

서울 청년 예비창업자가 나이 · 자본금 · 경력 · 자격증 · 희망 업종을 입력하면, 받을 수 있는 창업 지원금을 반영한 **자치구별 가용 예산**을 계산하고, 그 예산으로 자치구 평균 임대비용을 감당할 수 있는 곳의 **행정동을 예상 매출 · 생존기간 · 성장세 순으로 추천**하는 웹 서비스다.

핵심은 '조회'가 아니라 **'역산'**이다. 위치를 먼저 정하지 않고, 지원금을 예산으로 환산해 지역을 거꾸로 찾는다. 상권 분석은 이미 여러 서비스가 하고 있지만, 지원사업을 구조화해 예산으로 바꾸는 일은 아무도 하지 않았다. 차별점은 그쪽에 있다.

### 1.2 두 덩어리 — 미리 해두는 일과 요청 때 하는 일

| 구분 | 언제 | 하는 일 |
| --- | --- | --- |
| **① 배치** | 사용자와 무관하게. 지원사업은 매주 EC2에서, 학습 · 예측 · 요약은 분기 1회 팀원 PC에서 | 공공데이터 수집 · 정리, 모델 학습, 전 조합 예측, 종합점수 계산, LLM 요약 생성 → **서빙 표 4개**를 채운다 |
| **② 요청 시** | 사용자가 버튼을 누를 때 | 서빙 표를 조회해 **가용 예산과 예산 여유만 새로 계산**하고, 나머지는 읽어서 정렬한다 → 1초 이내 응답 |

어려운 계산은 전부 ①에서 끝나 있다. 요청 경로에는 모델도, 무거운 연산도 없다.

![타운시그널 시스템 구조 — 배치와 요청의 2단 분리](https://raw.githubusercontent.com/Town-Signal/TownSignalServer/develop/docs/figures/structure_v0.9.png)

*[그림 1] 시스템 구조 — 배치(실행 위치 구분)와 요청의 2단 분리*

| 표 | 행 수 | 내용 | 만드는 곳 · 주기 |
| --- | --- | --- | --- |
| support_program 지원사업표 | 수백 | 사업명 · 금액 · 적용 자치구 · 중복수혜 불가 여부 · 자격조건 트리 · 공고 원문. 검수된 행만 매칭 | 백엔드 · 매주 |

## 2. 원칙과 저장소

### 2.1 3대 원칙 (설계서 v1.5)

| 원칙 | 내용 | 이유 |
| --- | --- | --- |
| 2단 분리 | 배치가 서빙 표를 미리 채우고, 요청 시에는 조회와 사칙연산만 한다. 모델 서빙 서버는 두지 않는다 | 42,600행은 미리 다 계산해도 작은 규모다. 요청 경로에서 무거운 연산을 없애면 속도와 안정성이 함께 확보된다 |
| 동기식 + common 공유 | async를 쓰지 않는다. 자격 판정 · 예산 · 점수 로직을 common/에 두고 배치와 API가 같은 코드를 쓴다 | 요청 경로에 외부 대기가 거의 없어 async의 이득이 없다. 같은 코드를 쓰면 배치와 API의 결과가 어긋나지 않는다 |
| Redis 배제 | 캐시 서버를 두지 않는다. LLM 요약은 summary_cache 테이블로 충분하다 | 인프라가 하나 늘면 팀원 5명이 각자 띄워야 한다 |

### 2.2 저장소

| 저장소 | 내용 | 담당 |
| --- | --- | --- |
| **TownSignalServer** (기본 브랜치 develop) | 파이썬 전부 — api · batch · common · data · docs | 박규민 · 노현석 · 노승민 · 이성진 |
| **TownSignalFE** | React SPA | 한석희 |

TownSignalAI는 학습 코드가 batch/로 들어가면서 2026. 09. 30. 삭제했다.

```
TownSignalServer/
├── api/          FastAPI 동기식. DTO는 api/schemas/에만        ← common import
├── batch/        수집 · 전처리 · 학습 · 점수 선계산 · 표 생성   ← common import
│   └── jobs/     python -m batch.jobs.<작업명> 으로 실행
├── common/       evaluator · budget · scoring · constants (순수 함수)
├── data/         raw · processed · seed
├── docs/         이 문서 · 구조도
├── tests/
├── Dockerfile          api 이미지
├── Dockerfile.batch    batch 이미지
└── docker-compose.yml  db + api (+ batch 프로필)
```

- **common/**은 FastAPI · Pydantic · DB에 의존하지 않는 순수 함수만 둔다.
- **이미지를 둘로 나눈다.** 예측은 prediction 표에서 읽으므로 API 이미지에는 xgboost 등 학습 라이브러리와 모델 파일이 없다.
- **프론트는 합치지 않는다.** common/을 공유하는 건 파이썬 쪽뿐이고, 프론트는 툴체인(Node/Vite)과 배포 대상(Vercel)이 다르다. 프론트와 서버는 API 명세로만 엮인다.

## 3. 요청 흐름 — 사용자가 버튼을 누를 때

### 3.1 전체 흐름

추천은 두 번의 요청으로 나뉜다. 먼저 자치구별 가용 예산을 보여주고, 사용자가 확인한 뒤 추천을 받는다.

| 단계 | 화면 | API | 하는 일 |
| :---: | --- | --- | --- |
| 1 | 조건 입력 | — | 나이 · 자본금 · 경력 · 자격증 · 희망 업종 입력 |
| 2 | 자치구별 예산 확인 | POST /api/programs/calculate-budgets | 지원사업 판정 → 25개 자치구별 가용 예산 · 임대비용 · 예산 여유 · 통과 여부 계산 → 결과를 스냅샷으로 저장하고 rec_id 발급 |
| 3 | 추천 행정동 확인 | POST /api/recommendations (rec_id만 받음) | 통과 · 확인불가 자치구의 행정동을 모아 prediction의 종합점수로 정렬 → 요약 캐시와 함께 반환 |

3단계는 rec_id만 받는다. 조건을 다시 받으면 2단계를 건너뛸 수 있기 때문이다. 3단계는 2단계 스냅샷을 읽기만 하고 재계산하지 않는다.

### 3.2 예시 — 27세 · 자본금 3,000만 원 · 조리기능사 · 한식음식점 · 33㎡

*수치는 설명용 가상값이다.*

![요청 예시 — 27세 · 자본금 3,000만 원](https://raw.githubusercontent.com/Town-Signal/TownSignalServer/develop/docs/figures/example_v0.9.png)

*[그림 2] 요청 예시 — 지원금 매칭 → 가용예산 · 임대비용 · 판정 → 추천 정렬*

**① 지원사업 판정.** 자치구마다 따로 판정한다. 한 번만 계산하면 25개 구의 예산이 전부 같아져 서비스의 핵심이 사라진다.

| 사업 | 금액 | 범위 | 중복수혜 | 결과 |
| --- | --- | --- | --- | --- |
| 청년창업사관학교 | 2,000만 | 전국 | 불가 | 선택 |
| 서울시 청년도약지원금 | 1,000만 | 전국 | 불가 | 제외 — 더 큰 사관학교와 중복 불가 |
| 관악구 청년창업지원금 | 500만 | 관악구 | 가능 | 관악구만 선택 |

중복수혜 불가 사업 중에서는 금액이 가장 큰 하나만, 가능한 사업은 전부 더한다.

**② 가용 예산 · 임대비용 · 예산 여유.**

```
가용 예산     = 자본금 + 지원금 합계
월세         = 자치구 ㎡당 월세(천원) × 1,000 × 희망 면적
추정 임대비용 = 보증금(월세 × 15) + 월세 × 3  =  월세 × 18
예산 여유     = 가용 예산 − 추정 임대비용
```

| 자치구 | 가용 예산 | ㎡당 월세 | 추정 임대비용 | 예산 여유 | 판정 |
| --- | --- | --- | --- | --- | --- |
| 관악구 | 5,500만 | 28.5천원 | 1,692.9만 | +3,807.1만 | **통과** |
| 중구 | 5,000만 | 95.0천원 | 5,643만 | −643만 | **제외** |
| 도봉구 | 5,000만 | 없음 | — | — | **확인불가** (탈락시키지 않음) |

- 임대비용은 자치구 평균이라 같은 구의 행정동은 모두 같은 값을 쓴다. 권리금 · 인테리어 · 집기는 포함하지 않으며 화면에 그렇게 적는다.
- 임대료 자료가 없는 구(도봉구)는 0원으로 두지 않는다. 0원으로 두면 가장 싼 곳으로 1위가 되기 때문이다.

**③ 추천 행정동 정렬.** 통과 · 확인불가 자치구의 행정동에 대해 prediction에서 희망 업종의 행을 꺼내 **종합점수** 순으로 정렬한다. 종합점수는 배치가 미리 계산해 둔 값이다(5.5).

```
종합점수 = 100 × (0.4 × 매출 백분위 + 0.4 × 생존 백분위 + 0.2 × 성장세 백분위)
  백분위: 같은 업종의 서울 전체 행정동 안에서의 위치 (0 ~ 1)
  값이 없는 항목은 빼고 남은 가중치를 비례로 늘린다 (성장세가 없으면 매출 50 · 생존 50)
  예산 여유는 점수에 넣지 않는다 (자치구 단위 추정치라 오차가 순위 전체로 번진다)
```

**④ 결과.** 추천 행정동 순위와 함께 항목별 근거(매출 · 생존 · 성장세의 원값 · 백분위 · 기여도), 예산 여유, 요약 문장을 내린다.

### 3.3 요청 경로의 LLM

LLM 호출은 보통 몇 초가 걸려 1초 원칙과 충돌하므로, 요청 경로에서는 원칙적으로 부르지 않는다.

| 문장 | 방식 |
| --- | --- |
| 행정동 × 업종 요약 | 배치가 미리 만든 summary_cache 조회. 없으면 null을 내리고 프론트가 템플릿 문장으로 대신한다 |
| 사용자별 예산 문장 | 프론트 템플릿 (사용자마다 달라 미리 만들 수 없음) |
| **예외 — 자격증 자유 입력** | 동의어 사전에 없는 자격증만 요청 중에 LLM으로 표준명에 맞춘다. 타임아웃 2초, 실패하면 원문 그대로 진행 |

### 3.4 응답 시간 (목표 1초)

| 단계 | 예산 | 근거 |
| --- | --- | --- |
| 지원사업 판정 · 예산 합산 | 100ms | 수백 행을 메모리에서 판정, 25회 반복 |
| 임대료 조회 · 여유 계산 | 100ms | 25행 |
| 예측표 조회 | 200ms | 통과 구의 행정동 × 희망 업종. 점수는 선계산값 조회 |
| 정렬 · 근거 분해 · 요약 캐시 조회 | 100ms | 메모리 연산 + 기본키 조회 |
| 네트워크 · 직렬화 | 약 500ms | |
| (예외) 자격증 LLM 폴백 | 최대 2초 | 사전에 없는 자격증이 있을 때만 |

### 3.5 예외 처리

| 상황 | 처리 |
| --- | --- |
| 매칭되는 지원사업이 없음 | 자본금만으로 계산하고 그 사실을 화면에 표시 |
| 임대료 자료가 없는 자치구 | '확인불가'로 후보에 남기고 "임대비용 정보 없음" 배지 |
| 추천 후보가 0개 | 빈 목록 + 조건 다시 입력 안내 (오류 아님) |
| 표본이 적은 조합 (점포 5개 미만) | 순위에 포함하고 "표본이 적어 신뢰할 수 없음" 표시 |
| 예측 행이 없는 조합 | 후보에서 빼고 "예측 불가" 표시 |
| 요약 캐시 없음 | 요약 영역을 템플릿으로 대체 |
| 배치 실패 | 직전 표 유지. 표 교체는 트랜잭션으로 해서 부분 갱신을 막음 |

API 경로 · 필드 · 공통 응답 형식의 최종 정의는 전체 명세 8장 · 9장을 따른다.

### 4.5 행정동 단위 임대료 (2순위 과제)

## 5. AI 모델

### 5.1 구성

학습 모델은 두 개이고 모두 배치에서만 돈다. 종합점수도 배치에서 계산한다. 지원금 매칭은 학습이 아니라 규칙 판정이다. 학습 · 예측 배치는 **팀원 PC에서 실행하고 결과 표만 운영 DB에 넣는다**(6.2). 운영 서버에는 모델 파일도, 추론도 없다.

| 구성요소 | 방식 | 출력 | 실행 |
| --- | --- | --- | --- |
| 모델 A — 매출 | XGBoost 분위수 회귀 | 행정동 × 업종의 점포당 분기 매출 p10 · p50 · p90 | 배치 |
| 모델 B — 생존 | XGBoost AFT (생존 분석) | 행정동 × 업종의 생존기간(개월) p10 · p50 · p90 | 배치 |
| 성장세 | 매출 시계열 파생 | 최근 1년 ÷ 직전 1년 − 1 | 배치 |
| 종합점수 | 백분위 가중합 | 백분위 3종 · 종합점수 · 순위 | 배치 (선계산) |
| LLM ① | 공고 구조화 | 지원사업표 행 | 배치 · 매주 |
| LLM ② | 요약 생성 | 행정동 × 업종 요약문 | 배치 · 기준 분기 변경 시 |
| LLM ③ | 자격증 정규화 폴백 | 표준 자격증명 | 요청 시 · 사전 미등록일 때만 |

p10 · p50 · p90은 **80% 예측구간**이다. '최소 · 최대'라고 부르지 않는다.

### 5.2 모델 A — 점포당 분기 매출

**① 타깃 (확정 — 전체 명세 15장 2번).** 타깃 = 분기 매출 ÷ 점포 수(같은 행정동 · 업종 · 분기). 원천 매출은 행정동 × 업종 총액이라, 총액을 예측하면 점포가 많은 동네가 무조건 1등이 된다. 점포 수가 0이거나 없는 행은 학습에서 뺀다. 저장 · 계산은 분기 기준이고 화면은 월 매출(÷ 3)로 보여준다.

**② 피처.**

| 구분 | 피처 | 출처 |
| --- | --- | --- |
| 업종 · 지역 | 업종 · 자치구 · 행정동 코드 | 마스터 |
| 경쟁 | 점포 수, 프랜차이즈 점포 수, 개업 수, 폐업 수 | store_quarterly |
| 수요 | 유동인구 총계, 성별 · 연령대 · 시간대 분포 | population_quarterly |
| 비용 | 자치구 ㎡당 월세 | district_rent |
| 시간 | 분기(계절성), 직전 분기 · 전년 동기 점포당 매출, 공간 기준 변경 플래그 | 파생 |

**③ 알고리즘.**

| 구분 | 알고리즘 | 역할 |
| --- | --- | --- |
| 기준선 | 직전 분기 값 그대로(naive), 선형 회귀, RandomForest | 모델이 의미 있는지 판단하는 하한 |
| 주력 | XGBoost, 목적함수 reg:quantileerror (0.1 · 0.5 · 0.9) | model_version xgb_v1 |
| 비교군 (2순위) | MLP (PyTorch) | 계획서의 딥러닝 비교 요구. 같은 분할 · 피처, mlp_v1 |

**④ 전처리.** 타깃에 log1p를 적용하고 평가는 원 단위로 되돌린다. 최근 4개 분기 평균 점포가 5개 미만인 조합은 학습에서 빼되 예측은 만들어 '표본 부족'으로 표시한다. 업종 코드의 타깃 인코딩은 학습 분할 안에서만 계산한다.

**⑤ 분할과 2024년 처리 (확정 — 전체 명세 15장 13번).** 무작위 분할은 쓰지 않는다. 같은 동의 인접 분기가 학습 · 테스트에 함께 들어가 성능이 부풀려진다.

| 구분 | 결정 |
| --- | --- |
| 시간 분할 | 마지막 2개 분기 = 테스트, 그 앞 2개 분기 = 검증, 나머지 = 학습. 최신이 2025Q4라면 테스트 2025Q3~Q4, 검증 2025Q1~Q2, 학습 2021Q1~2024Q4 |
| 2024년 처리 (주 방식) | 전 기간으로 학습하고 공간 기준 변경 플래그(2024Q1 이후 = 1)를 넣는다. 경계를 넘는 시차 피처(2024Q1의 직전 분기, 2024년 분기의 전년 동기)는 결측으로 둔다 |
| 2024년 처리 (비교군) | 2024Q1 이후만으로 학습. 검증 손실이 더 낮으면 이쪽을 채택 |
| 최종 적재 | 하이퍼파라미터를 고정한 뒤 전 기간으로 다시 학습해 전 조합을 예측. 보고하는 성능은 재학습 전 테스트셋 값 |

검증 · 테스트가 모두 2024년 이후라, 서비스가 실제로 쓰는 공간 기준으로 평가된다.

**⑥ 예측 구간.** 세 분위수 값을 조합마다 정렬해 p10 ≤ p50 ≤ p90을 보장한다. 분위수 회귀는 시간이 흐른 구간에서 포함률이 모자라기 쉬우므로, 검증 분기의 잔차로 구간 폭을 보정한 뒤 테스트 포함률을 보고한다.

### 5.3 모델 B — 생존기간

**① 문제.** 인허가의 개업일 · 폐업일로 영업 기간을 모델링한다. 아직 영업 중인 점포는 실제 기간을 모르므로(우측 절단) 일반 회귀가 아닌 생존 분석을 쓴다. 폐업 점포만 학습하거나, 영업 중 점포의 현재 기간을 정답으로 쓰거나, 영업 중 점포를 빼면 모두 생존기간이 짧게 추정된다.

**② 알고리즘.**

| 구분 | 알고리즘 | 비고 |
| --- | --- | --- |
| 기준선 | 업종별 Kaplan–Meier 중앙값, Cox 비례위험 (lifelines) | 위험 요인 설명 |
| 주력 | XGBoost AFT (survival:aft) | 생존시간 분포를 직접 추정해 p10 · p50 · p90을 바로 낸다. 모델 A와 라이브러리가 같다 |
| 선택 | Random Survival Forest (scikit-survival) | 여력이 있으면 비교 |

레이블은 하한 = 영업기간(개월), 상한 = 영업기간(폐업) 또는 무한대(영업 중). 분포(normal · logistic · extreme)와 scale은 검증셋으로 고른다.

**③ 피처와 관측 한계.** 점포의 **개업 분기 시점** 행정동 × 업종 상권 지표만 붙인다(폐업 이후 정보는 누수). 상권 지표가 2021년 이후뿐이라 학습은 2021년 이후 개업 점포로 한정되고, 관측 기간은 최대 약 60개월이다. 전 조합 예측은 최신 분기 지표로 '지금 개업하는 점포'를 가정한다.

**④ 분할 (확정 — 전체 명세 15장 13번).** 개업 분기 기준 — 학습 2021~2022년, 검증 2023년, 테스트 2024년 이후. 테스트 점포는 관측이 짧아 절단 비율이 높으므로 절단을 고려한 C-index(Uno)도 함께 보고한다. 최종 적재 전에는 전 기간으로 다시 학습한다.

**⑤ 출력 (확정 — 전체 명세 15장 3번).**

| 항목 | 결정 |
| --- | --- |
| 주 출력 | 생존기간 개월 p10 · p50 · p90 |
| 1년 · 3년 생존확률 | 같은 분포에서 추가 비용 없이 계산된다. 2순위로 prediction에 보조 칼럼 추가를 제안(백엔드 합의 필요). 1순위 화면에는 넣지 않는다 |
| 외삽 표기 | 60개월을 넘는 값은 외삽이다. 화면에서 '60개월 이상'으로 표기할 것을 제안 |
| 순위 영향 | AFT는 모든 조합이 같은 scale을 쓰므로 어느 분위수로 정렬해도 순서가 같다. p50이 외삽이어도 생존 백분위는 흔들리지 않는다 |

### 5.4 성장세

```
성장세 = 최근 4개 분기 점포당 매출 합 ÷ 직전 4개 분기 합 − 1
  두 구간 모두 2024Q1 이후 분기만 쓴다
  경계 이후 분기가 8개 이상 → 신뢰도 '높음'
  4 ~ 7개 → '낮음'
  4개 미만 → 계산하지 않음 (화면 '데이터 없음')
```

4~7개일 때 전체 명세 6.4는 ⌊k/2⌋ 분기씩 비교한다. 이러면 두 구간의 분기 구성이 달라 계절성이 상쇄되지 않으므로, 최근 (k − 4)개 분기를 1년 전 같은 분기와 비교하는 방식을 제안한다. 최신이 2025Q4면 k = 8이라 1차 적재에는 영향이 없다.

### 5.5 전 조합 예측과 종합점수 선계산

학습이 끝나면 42,600개 조합 전체를 예측하고, 같은 배치에서 점수까지 계산해 한 번에 적재한다.

```
1. 모델 A · B로 전 조합 예측 → 분위수 순서 보정
2. 성장세 계산
3. 같은 업종 · 같은 모델 버전 안에서 백분위 (PERCENT_RANK, 값이 없는 행은 제외)
4. 종합점수 = 100 × Σ (재배분된 가중치 × 백분위), 소수 1자리
5. 순위 = 같은 업종 안 종합점수 순 (동률은 행정동 코드 순)
6. 스테이징 표에 적재 → 한 트랜잭션에서 교체, 해당 요약 캐시 삭제
```

**선계산은 채택한다.** 백분위의 비교 대상이 '같은 업종의 서울 전체 행정동'이라 요청과 무관하게 미리 계산할 수 있다. 요청 경로는 읽기만 하게 되고, 추천 밖 화면(직접 찾아보기 · 상세 · 비교)도 같은 점수를 보여준다. 단 아래 조건을 붙인다.

| No | 조건 | 이유 |
| :---: | --- | --- |
| 1 | 점수는 예측값과 같은 트랜잭션에서만 갱신 | 예측과 점수가 다른 시점 값이면 근거 분해가 맞지 않는다 |
| 2 | '표본 부족' 행도 백분위 계산에 포함 | 순위에 포함하는 규칙(판정 20)과 일관. 예측값은 모델 출력이라 소표본 노이즈가 직접 들어가지는 않지만, 검증 때 이 행들이 상위에 몰리지 않는지 점검 |
| 3 | 성장세 결측 비율 감시 | 결측 재배분 때문에 행마다 가중치가 다르면 점수 척도가 조금씩 달라진다. 결측이 20%를 넘으면 결측을 0.5로 두는 방식과 비교 |
| 4 | 표본 부족 판정도 선계산 (칼럼 추가 제안) | 요청과 무관한 값이라 미리 두면 랭킹 · 추천이 같은 판정을 쓰고 응답이 가볍다 |
| 5 | 학습 원천의 최신 분기 기록 (칼럼 추가 제안) | 어느 분기 데이터로 만든 예측인지 남기고, 배치 재생성 판단에도 쓴다 |

4 · 5번 칼럼 추가는 DB 변경이라 백엔드와 합의해 반영한다.

### 5.6 LLM (확정 — 전체 명세 15장 12번)

LLM은 숫자를 만들지 않는다. 공고문을 정리하고, 서버가 계산한 값을 문장으로 옮기고, 자격증 이름을 표준 목록에 맞추는 일만 한다. 요약문과 화면 수치가 다르면 화면 수치가 정본이다.

| 작업 | 모델 · 방식 | 범위 · 제한 |
| --- | --- | --- |
| ① 공고 구조화 (매주) | claude-opus-5-5, JSON 스키마 구조화 출력, Batch API | 검수자가 기록된 행만 매칭. 모호한 요건은 판단보류로 매칭에서 제외 |
| ② 요약 생성 (기준 분기 변경 시, PC에서 요청) | 기본 claude-opus-5-5, Batch API + 공통 지시문 캐싱. 표본 50건을 모델별로 비교한 뒤 더 싼 모델로 내릴지 팀이 결정 | 표본 정상 · 점포 5개 이상 조합만(약 2만 건 가정). 1순위 릴리스에서는 생성하지 않음 |
| ③ 자격증 폴백 (요청 시) | 2초 안에 끝나는지 실측 후 모델 확정. 표준 목록 중 하나 또는 '없음'만 출력 | 타임아웃 2초 · 재시도 없음. 실측 전까지 끄는 설정 플래그. 폴백 로그로 동의어 사전 보강 |

### 5.7 성능 목표와 현실성

| 항목 | 목표 | 현실성 | 조치 |
| --- | --- | --- | --- |
| 매출 R² (p50) | 0.6 이상 | **너무 쉽다.** 직전 분기 매출이 피처에 있으면 그대로 베끼기만 해도 0.6을 넘기 쉽다 | 목표는 유지하고 **naive 대비 MAE 개선율**을 함께 보고. R²는 원 단위 · log 단위 둘 다 |
| 생존 C-index | 0.7 이상 | **도전적이다.** 피처가 행정동 × 업종 단위라 같은 칸 점포끼리는 구분 못 한다. 업종 간 차이가 커 전체 C는 0.7 근처가 가능하지만 업종 내 C는 0.6 안팎 예상 | 목표 0.7 유지, **하한 0.65**. 업종 내 C 별도 보고. 점포 단위 필드(시설 면적 등) 피처 검토 |
| 80% 구간 포함률 | 80%에 근접 | 보정 없이는 모자랄 수 있다 | 검증 분기로 구간 보정 후 측정 |
| 지원사업 추출 정확도 | 30건 · 필드 일치율 85% | 판단보류를 빼고 재면 현실적 | 백엔드 측정 |
| 응답 속도 | 1초 이내 | 점수 선계산으로 여유 | 자격증 폴백 요청만 최대 2초 |

### 5.8 딥러닝을 주력으로 두지 않는 이유

데이터가 수만 행 규모의 정형 표라 트리 앙상블이 더 안정적이고, 추천 근거를 항목별로 설명해야 해서 해석이 쉬운 모델이 유리하다. 계획서의 딥러닝 비교 요구는 같은 조건으로 MLP를 학습해 수치로 비교하는 실험으로 충족한다.

### 6.3 AI는 어디서 도는가

![AI는 어디서 도는가](https://raw.githubusercontent.com/Town-Signal/TownSignalServer/develop/docs/figures/ai_runtime_v0.9.png)

*[그림 3] AI 실행 위치 — 학습은 팀원 PC, LLM은 Anthropic API, EC2는 결과 표만 읽는다*

| AI | 실행 위치 | 주기 | 결과 |
| --- | --- | --- | --- |
| 모델 A · B 학습, 전 조합 예측, 성장세 · 종합점수 | 팀원 PC | 분기 1회 | prediction 표 → 운영 DB |
| LLM ① 공고 구조화 | Anthropic API (요청은 EC2 주간 배치. 안정되기 전에는 PC에서 수동) | 매주 | support_program 표 |
| LLM ② 요약 | Anthropic API (요청은 PC) | 분기 1회 | summary_cache 표 → 운영 DB |
| LLM ③ 자격증 폴백 | Anthropic API (요청은 EC2의 API) | 요청 중, 드물게 | 응답에 바로 사용 |

**학습을 EC2에 올리지 않는 이유.**
- 학습은 분기에 한 번뿐이라 서버에서 자동화할 이득이 작다.
- API는 prediction 표만 읽으므로 모델 파일이 서버에 있을 필요가 없다.
- 학습(특히 공간 조인 · 전 조합 예측) 순간의 메모리를 EC2가 감당하려면 인스턴스를 키워야 한다. PC에서 돌리면 EC2는 API와 DB만 돌리는 작은 인스턴스로 충분하다.
- 문제가 생기면 PC에서 바로 보고 고칠 수 있다.

**지켜야 할 것.**
- 운영 DB 포트는 외부에 열지 않는다. PC에서 EC2 키로 SSH 터널을 열고 DATABASE_URL만 바꿔 적재 스크립트를 실행한다. 표 교체는 한 트랜잭션으로 한다.
- 학습은 저장소의 batch 코드로만 돌린다. 노트북 셀에서 만든 결과는 적재하지 않는다.
- 모델 파일과 학습 지표(JSON)를 model_version별로 팀 드라이브나 S3에 올려 재현할 수 있게 한다.
- 나중에 자동화하려면 PC에서 최대 메모리 사용량을 재 보고, EC2에 API · DB를 빼고도 여유가 있을 때 메모리 · CPU 제한을 걸고 새벽에만 실행한다(12주차 이후 판단).
