## 설계서 v1.5 — 3대 원칙

- **2단 분리** — 배치가 support_program · district_rent · prediction 세 표를 미리 채움. 요청 시에는 조회와 사칙연산만 하므로 1초 이내 응답. **모델 서빙 서버 없음**
- **동기식 + common 공유** — async를 쓰지 않음. 자격요건 평가기와 예산 로직을 배치와 API가 같은 모듈로 공유해 로직 불일치를 차단함
- **Redis 배제** — LLM 요약은 summary_cache 테이블로 충분. 인프라 하나 늘리면 팀원 5명이 각자 띄워야 함

> ⚠️ **v0.6 조정 — 배치 주기를 나눈다**
>
> cron은 주 1회로 두되, 매주 다시 만드는 것은 지원사업표뿐이다. 임대료표 · 예측표 · 요약 캐시는 원천(상권 · 인구)이 분기 갱신이라 **기준 분기가 바뀐 주에만** 재생성한다. 매주 재학습해도 값은 그대로인데 학습 비용만 든다.

## 저장소 구성

| 저장소 | 내용 | 담당 |
| --- | --- | --- |
| **TownSignalServer** | 파이썬 전부 — api · batch · common · data | 박규민 · 노현석 · 노승민 · 이성진 |
| **TownSignalFE** | React SPA | 한석희 |
| ~~TownSignalAI~~ | **삭제됨(2026. 09. 30.).** 학습 코드는 TownSignalServer의 batch/에 둔다 | — |

```
TownSignalServer/
├── api/          # FastAPI 동기식. DTO는 api/schemas/에만   ← common import
├── batch/        # 수집 · 전처리 · 학습 · 표 생성            ← common import
│   └── jobs/     # python -m batch.jobs.<작업명> 으로 실행
├── common/       # evaluator · budget · scoring · constants (Pydantic 없음)
├── data/         # raw · processed · seed   → 데이터 파이프라인 페이지
├── tests/
├── Dockerfile          # api 이미지
├── Dockerfile.batch    # batch 이미지
└── docker-compose.yml
```

**프론트는 합치지 않는다.** `common/`을 공유해야 하는 건 파이썬 쪽(api · batch)뿐이다. 프론트는 툴체인(Node/Vite)과 배포 대상(Vercel)이 달라, 합치면 CI에 경로 필터만 늘어난다. 나눠두면 전부 파이썬이라 테스트를 그냥 다 돌리면 된다.

**이미지를 둘로 나눈다.** 예측을 요청 때 계산하지 않고 prediction 표에서 읽기 때문에 **API 이미지에는 xgboost · scikit-survival이 필요 없다.** 배치만 학습 의존성을 가진다. API는 모델 파일을 로드하지 않는다.

## v0.9에서 바뀐 것 — AI 파트 검토

2026. 09. 30. 「타운시그널 전체 명세」 v1.6의 AI 파트를 검토했다. 검토 범위는 6장 모델, 7.6~7.9 후보 선정 · 종합점수 · 정렬, 13장 판정 1 · 6 · 7 · 8 · 9 · 20 · 22 · 30이다.

### 확인한 것

| 질문 | 결론 | 근거 · 조건 |
| --- | --- | --- |
| 종합점수를 배치에서 미리 계산해도 되는가(v1.6 6.5) | **된다.** 채택 | 백분위 모집단이 '같은 업종의 서울 전체 행정동'이라 요청과 무관하다. 요청 경로가 읽기만 하게 되어 3원칙과 맞고, 추천 밖 화면에서도 같은 점수를 보여줄 수 있다. 조건 5가지는 5.5 |
| 성능 목표가 현실적인가 | **R²는 너무 쉽고, C-index는 도전적이다** | R²는 직전 분기 매출 피처만으로도 넘을 수 있어 naive 대비 개선율을 함께 본다. C-index는 피처가 행정동 × 업종 단위라 같은 칸 점포를 구분하지 못해 하한 0.65를 둔다. 상세는 5.8 |

## v0.6에서 바뀐 것 — 저장소 구조가 실제로 바뀌었다

2026.09.26 기준. PR #4가 main에 머지됐고 CI도 통과했다.

1. **저장소 이름을 바꿨다.** `TownSignalBE` → `TownSignalServer`. 백엔드와 AI · 데이터가 한 저장소에 들어가므로 BE라는 이름이 맞지 않는다. 로컬 클론이 있으면 `git remote set-url origin https://github.com/Town-Signal/TownSignalServer.git`로 정리한다(깃허브가 리다이렉트는 해준다).
2. **Spring 뼈대를 걷어내고 FastAPI 구조를 넣었다.** `api/ batch/ common/ data/ tests/`. `common/`에는 자격 판정 · 가용예산 · 순위 산정 함수와 테스트 15개가 들어가 있다.
3. **CI · 배포를 파이썬 기준으로 갈아끼웠다.** ruff + pytest, ECR → EC2 흐름과 IAM Role은 그대로 재사용, 설정값만 환경변수 주입으로. 이미지 태그에 커밋 SHA를 붙여 롤백이 가능하다.
4. **프론트는 합치지 않기로 확정했다.** 위 '저장소 구성' 참조.
5. **API 이미지와 배치 이미지를 분리했다.** API에는 학습 라이브러리를 넣지 않는다.
6. **TownSignalAI는 보관 처리 예정이다.** 내용이 README뿐이고 학습 코드는 `batch/`로 들어갔다. → 2026. 09. 30. 저장소 삭제(v0.9).

## 왜 두 덩어리로 나뉘는가

이 서비스에서 헷갈리는 지점은 하나이다. **어떤 일이 미리 끝나 있고, 어떤 일이 사용자 요청 때 일어나는가.** 계획서는 기술 나열과 기능 나열이 섞여 있어 이 구분이 보이지 않는다.

어려운 계산은 전부 ①에서 끝나 있고, 사용자 요청(②)은 만들어둔 표를 조회해 더하고 빼는 일만 한다. 계획서의 "응답 10초 이내"는 이 구조에서 **1초 이내**로 줄어든다.

요청 시에 새로 계산하는 값은 **가용예산 · 예산 여유 두 가지뿐**이다. 종합점수는 v0.9부터 배치가 미리 계산해 둔다(5.5). 나머지는 전부 조회다.

## ① 배치 — 미리 만들어두는 표

프로젝트의 **약 80%가 여기에 있다.** 사용자가 오기 전에 완성돼 있어야 한다. 아래 표는 전체 명세 v1.6(schema.sql) 기준이다.

| 표 | 크기 | 내용 | 만드는 법 | 담당 · 주기 |
| --- | --- | --- | --- | --- |
| **지원사업표** `support_program` | 수백 행 | 사업명 · 금액 · 적용 자치구 · 중복수혜 불가(is_exclusive) · 자격조건 트리(eligibility JSONB) · 공고 원문 | 공고문을 LLM으로 구조화 → 원문과 대조해 사람이 검수. `verified_by`가 있는 행만 매칭에 사용 | 백엔드 (박규민·노현석) · 주 1회 |

**매출은 점포당으로 잡는다(v0.9 확정).** 원천(OA-22175)의 매출은 행정동 × 업종 총액이라 그대로 예측하면 점포가 많은 동네가 무조건 1등이 된다. 타깃 = 분기 매출 ÷ 점포 수(OA-22172와 결합). → 5.2절

**생존기간은 생존분석으로 한다.** 아직 영업 중인 가게는 실제 영업 기간을 모르는 상태(우측 절단)라 일반 회귀로 풀면 생존 기간이 짧게 추정된다. 출력은 생존기간 개월 구간(p10 · p50 · p90)이고, 관측 기간(최대 약 60개월)을 넘는 값은 외삽이므로 표기에 주의한다. → 5.3절

## ② 요청 시 — 사용자가 버튼 누를 때

> 💡 **v1.6 기준 흐름**
>
> 가용예산은 하나(자본금 + 지원금 최대 합계)이고, 임대비용은 자치구 평균(월세 × 18)이며, 순위는 배치가 미리 계산한 종합점수를 읽는다. 아래 예시의 보수/기대 예산 · 행정동 초기비용은 v0.5 권고 기록이다(전체 명세 판정 2 · 4 · 5로 미채택).

새로 계산하는 게 거의 없다. 아래는 **27세 · 자본금 3,000만원 · 조리기능사 보유 · 요식업 희망**이 들어왔을 때 일어나는 일이다. (수치는 설명용 가상값)

1. **조건 입력** — 나이 27 / 자본금 30,000,000 / 경력 0년 / 업종 요식업 / 자격증 조리기능사
2. **지원사업표와 대조** — 청년창업사관학교 20,000,000(전국 · **경쟁 선정**) · 관악구 청년창업지원금 5,000,000(관악구 한정)
3. **자치구별 가용예산 산출** — 구마다 다르다는 것이 이 서비스의 핵심

| 자치구 | 보수 (자본금 + 선정 절차 없는 지원) | 기대 (경쟁 선정 성공 가정) |
| --- | --- | --- |
| 관악구 | 30,000,000 | 55,000,000 |
| 강남구 | 30,000,000 | 50,000,000 |

4. **임대료표와 비교해 감당 못 할 곳 제거** — 여유 = 가용예산 − 초기비용

| 행정동 | 초기비용 | 기대 기준 | 보수 기준 |
| --- | --- | --- | --- |
| 신림동 (관악구) | 40,000,000 | +15,000,000 통과 | −10,000,000 선정 필요 |
| 역삼동 (강남구) | 120,000,000 | −70,000,000 탈락 | — |

5. **예측표에서 남은 동네를 꺼내 정렬 + 요약** — 배치가 미리 계산한 종합점수(매출 · 생존 · 성장세 백분위)로 순위 → 요약 캐시 조회, 없으면 템플릿

→ **추천 행정동 순위 + 추천 근거**

### 왜 '받을 수 있는 금액'을 둘로 나누는가 (v0.5 권고 기록)

창업 지원사업의 상당수는 요건만 맞으면 받는 돈이 아니라 **경쟁해서 선정**된다(청년창업사관학교가 그렇다). 자격 충족을 곧 수령으로 계산하면 가용예산이 실제보다 커지고, 추천 결과 전체의 신뢰가 무너진다. 융자는 갚아야 하는 돈이고 공간 · 교육 지원은 현금이 아니므로 보조금과 같이 더하면 안 된다.

필터는 기대 기준으로 하되, 각 추천 동에 **보수 기준 통과 여부를 배지로 함께 표시**한다. 지원금이 선택지를 넓힌다는 차별점은 살리면서, 어떤 결과가 선정을 전제로 하는지 사용자가 알 수 있다. → 7.3절. 채택 여부는 전체 명세 15장 1번.

### 요청 시에는 LLM을 (거의) 부르지 않는다

LLM 호출은 보통 몇 초가 걸려 1초 원칙과 충돌한다. 추천 요약은 사용자마다 예산 맥락이 달라 미리 만들어둘 수도 없다.

- **추천 결과 · 상세 요약** → summary_cache(행정동 × 업종) 조회. 없으면 null을 내리고 프론트가 템플릿 문장으로 대체
- **사용자별 예산 문장** → 프론트 템플릿(LLM 없음)
- **지원사업 공고 구조화 · 행정동 요약 생성** → 배치
- **유일한 예외 — 자격증 자유 입력 정규화 폴백.** 동의어 사전에 없는 자격증만 요청 중에 LLM으로 표준명에 매핑한다. 타임아웃 2초, 실패하면 원문 그대로 진행(전체 명세 판정 12)

→ 5.6절

| 배치 | 사용자 요청과 무관하게 주기적으로 실행되어 서빙 표를 채우는 작업. |
| 요청 시 | 사용자가 버튼을 누른 순간. 표 조회와 사칙연산만 수행한다. |
| 서빙 표 | 요청 시 조회되는 사전 계산 표. 지원사업표 · 임대료표 · 예측표 · 요약 캐시. |
| 가용 예산 | 자기 자본 + 받을 수 있는 지원금. 자치구마다 다르게 산출된다. |
| 보수 / 기대 예산 | 보수 = 자본금 + 선정 절차 없이 받는 지원. 기대 = 경쟁 선정 사업까지 모두 선정된다고 가정한 금액. (권고, 미채택) |
| 초기비용 | 자치구 평균 임대료로 계산한 보증금 + 월세 3개월(추정 임대비용). 임대료표가 제공한다. |
| 여유 | 가용 예산 − 초기비용. 0 미만이면 추천에서 제외한다. |
| 백분위 | 같은 업종 · 같은 모델 버전의 서울 전체 행정동 안에서의 상대 위치(0.0~1.0). 종합점수의 표준화 방식. |
| 우측 절단 | 관측 종료 시점까지 폐업하지 않아 실제 영업 기간을 모르는 상태. 생존 분석이 필요한 이유. |

## 2. 서비스 개요

### 2.1 서비스 정의

> 💡 **정의**
>
> 서울 청년 예비창업자가 인적 조건과 자본금을 입력하면, 받을 수 있는 창업 지원금을 반영한 자치구별 가용 예산을 계산하고, 그 예산으로 감당 가능한 창업 후보 행정동을 예상 매출 · 생존 가능성 순으로 추천하는 웹 서비스.

### 2.2 대상 사용자

서울에서 창업을 준비하지만 위치를 정하지 못한 만 39세 이하 예비창업자. 업종은 대략 정했으나, 자신이 어떤 지원사업에 해당하는지, 그래서 실제로 쓸 수 있는 돈이 얼마인지, 그 돈으로 어느 동네에 들어갈 수 있는지를 한 번에 파악하지 못한다.

### 2.3 해결하려는 문제

| 사용자가 겪는 문제 | 현재 상황 | 본 서비스의 해결 |
|---|---|---|
| 받을 수 있는 지원금을 모른다 | 공고가 기관별로 흩어져 있고 요건이 제각각 | 인적 조건을 요건과 규칙 기반으로 매칭해 금액 산출 |
| 지원금이 어느 동네를 의미하는지 모른다 | 지원사업 검색과 상권분석이 분리되어 이중 작업 | 가용 예산에서 초기비용을 빼 감당 가능한 지역만 남김 |
| 어디서 시작할지 모른다 | 기존 상권분석은 위치를 이미 정했다는 전제 | 조건만 입력하면 후보 행정동을 역으로 추천 |
| 얼마나 벌고 버틸지 모른다 | 현재 지표만 조회 가능 | 점포당 예상 매출과 예상 생존기간을 구간으로 제시 |

### 2.4 경쟁 서비스와의 차이

| 서비스 | 제공 방식 | 본 서비스와 겹치지 않는 지점 |
|---|---|---|
| 소상공인365 | 위치 지정 후 매출 · 유동인구 등 현재 지표 조회 | 예산 입력이 없고 지원사업은 안내 수준 |
| 서울시 골목상권 분석 | 행정동 · 업종 선택 후 조회, 매출 증감 자동 코멘트 | 조회는 정교하나 지원금 계산 · 지역 역추천은 없음 |
| 리치고 · 부동산지인 | 인구 · 공급 기반 주택 가격 예측 | 주거용 부동산 전용, 상권 · 창업은 다루지 않음 |
| K-Startup · 청년몽땅정보통 | 청년 창업 지원사업 공고 제공 | 공고만 제공, 상권분석과 연결되지 않음 |

상권 분석은 이미 골목상권이 정교하게 하고 있지만, **지원사업을 구조화해 예산으로 환산하는 일은 아무도 하지 않았다.** 차별점은 그쪽에 있다. 기존 서비스가 '이 동네가 어떤가'에 답한다면, 본 서비스는 '내 조건과 받을 수 있는 돈을 감안하면 어디가 유리한가'에 답한다.

### 2.5 MVP 범위

| 구분 | 포함 | 제외 (향후 과제) |
|---|---|---|
| 지역 | 서울 25개 자치구 · 426개 행정동 | 수도권 및 기타 광역시 |
| 사용자 | 청년 예비창업자 (지원사업 요건 기준) | 기존 사업자 이전 · 확장, 주거 입주자 관점 |
| 업종 | 서울시 상권분석서비스 업종 약 100개 | 프랜차이즈 브랜드 단위 분석 |
| 기능 | 지원금 계산, 지역 추천, 매출 · 생존 예측 조회, 상권 상세, 비교 | 실제 매물 연결, 사업계획서 작성, 신청 대행 |

### 3.4 저장소 구조

파이썬은 한 저장소에 모으고 프론트는 분리한다. 2026.09.26에 TownSignalBE를 TownSignalServer로 바꾸고 아래 구조로 교체했다(PR #4 머지 완료).

```
TownSignalServer/
├── api/          # FastAPI 동기식. DTO는 api/schemas/에만    ← common import
├── batch/        # 수집 · 전처리 · 학습 · 표 생성             ← common import
│   └── jobs/     #   python -m batch.jobs.<작업명> 으로 실행
├── common/       # evaluator · budget · scoring · constants   (Pydantic 없음)
├── data/         # raw · processed · seed   → 팀 「데이터 파이프라인」 페이지
├── tests/
├── Dockerfile          # api 이미지
├── Dockerfile.batch    # batch 이미지
└── docker-compose.yml

TownSignalFE/     # React SPA (별도 저장소)
```

| 디렉터리 | 역할 | 규칙 |
|---|---|---|
| common/ | 자격요건 평가(evaluator), 가용예산 계산(budget), 순위 점수(scoring), 상수 | 순수 파이썬 함수. 프레임워크(FastAPI · Pydantic · DB 세션)에 의존하지 않는다 |
| batch/ | 수집 · 전처리 · 임대료 집계 · 모델 학습 · 전 조합 예측 · 점수 선계산 · 공고 구조화 · 요약 생성 | API로 노출하지 않는다. cron 또는 수동으로 실행한다 |
| api/ | 요청 검증, 서빙 표 조회, common 호출, 응답 조립, 인증 | 모델 파일을 로드하지 않는다. 요청 DTO는 api/schemas/에만 둔다 |
| data/ | 원천 · 가공 · 시드 데이터 | 대용량 원천은 저장소에 올리지 않고 내려받기 스크립트로 관리한다 |
| (별도 저장소) web | 화면 | 계산 로직을 두지 않는다. 표시만 담당한다 |

> 💡 **프론트를 합치지 않는 이유**
>
> common/을 공유해야 하는 것은 파이썬 쪽(api · batch)뿐이다. 프론트는 common을 쓰지 않는다.
>
> 툴체인(Node/Vite)과 배포 대상(Vercel)이 달라 한 저장소에 넣으면 CI에 경로 필터가 필요해진다. 분리해두면 서버 저장소는 전부 파이썬이라 테스트를 그냥 다 돌리면 된다.
>
> 프론트와 서버는 코드가 아니라 API 명세로만 엮이고, 프론트는 한 사람이 담당한다.

> 💡 **이미지를 둘로 나누는 이유**
>
> 예측을 요청 때 계산하지 않고 prediction 표에서 읽으므로 API 이미지에는 xgboost · scikit-survival이 필요 없다. Dockerfile(api)과 Dockerfile.batch를 분리해 API 이미지를 가볍게 유지한다.
>
> 배치는 python -m batch.jobs.<작업명> 형태로 EC2 cron이 실행한다. 의존성이 겹치지 않아 배포와 학습을 따로 다룰 수 있다.

| 스키마 검증 | Pydantic v2 | api/schemas/ 에만 사용. common에는 두지 않음 |
| DB 접근 | SQLAlchemy 2.0 (동기 세션) + Alembic | 스키마 변경 이력 관리 |
| 인증 · 사용자 데이터 | 없음 (MVP). 최근 추천 · 즐겨찾기는 브라우저 localStorage | 기능명세서 v0.7에서 로그인 삭제. 관리자 API만 X-Admin-Token |
| 데이터베이스 | PostgreSQL 16 | 4.3절 선정 이유 |
| 캐시 | 없음 (summary_cache 테이블) | 3대 원칙: Redis 배제 |
| 배치 실행 | Python 스크립트 + cron | 배치 컨테이너를 cron이 실행 |
| 데이터 처리 | pandas · GeoPandas · pyarrow | 좌표 → 행정동 결합, 중간 산출물 Parquet |
| ML | XGBoost(분위수 회귀 · AFT) · scikit-learn · lifelines · scikit-survival | 모델 A · B는 XGBoost. lifelines는 Cox 기준선, scikit-survival은 C-index · 시간 의존 AUC 평가 |
| 딥러닝 비교군 | PyTorch (MLP) | 계획서의 딥러닝 비교 요구 충족 (2순위, mlp_v1) |
| LLM | Anthropic Claude API (anthropic 파이썬 SDK) | 배치(공고 구조화 · 요약)와 요청 시 자격증 정규화 폴백. 모델 · 비용은 5.6 |

| CI/CD · 배포 | GitHub Actions · AWS ECR → EC2 · Vercel | ruff + pytest, ECR→EC2 흐름 재사용 (10.2절) |

프론트 3행은 v0.9 검토 메모 참조(실제 코드와 다름).

### 4.2 동기식 FastAPI를 쓰는 이유

요청 경로가 DB 조회와 사칙연산만으로 끝나므로, 외부 API 대기를 겹쳐 처리해 이득을 보는 async의 장점이 발생하지 않는다. 동기식은 코드와 디버깅이 단순하고, 동기 스크립트인 배치와 common 모듈을 그대로 공유할 수 있다. FastAPI는 동기 핸들러(def)를 스레드 풀에서 실행하므로 동시 요청 처리에도 문제가 없다. 자격증 폴백의 LLM 호출도 드물고 타임아웃 2초라 스레드 풀 안에서 동기로 처리한다.

### 4.3 PostgreSQL을 쓰는 이유

| 항목 | PostgreSQL | MySQL |
|---|---|---|
| 분위수 집계 | percentile_cont로 중앙값 · 분위수를 한 번에 계산 | 중앙값 집계 함수가 없어 윈도우 함수로 우회 |
| 공간 데이터 | PostGIS 확장, GeoPandas read_postgis / to_postgis 직접 연동 | 공간 기능이 제한적이고 GeoPandas 직접 연동 없음 |
| 윈도우 함수 · CTE | 지원 | 8.0부터 지원 (차이 없음) |
| 전환 비용 | - | 초기 Spring 설정의 MySQL 드라이버는 2026.09.26 교체 때 함께 제거됨 |

백분위 선계산(PERCENT_RANK)과 분위수 집계를 반복하므로 윈도우 · 분위수 함수가 편한 PostgreSQL이 맞다. 엔티티와 스키마가 아직 없던 시점에 전환해 비용이 들지 않았다.

### 4.4 채택하지 않은 기술

| 후보 | 채택하지 않은 이유 |
|---|---|

### 5.1 구성 개요

### 5.2 모델 A — 점포당 분기 매출 (XGBoost 분위수 회귀)

#### 5.2.1 타깃 정의 (확정 — 15장 2번)

> ⚠️ **예측 대상은 총매출이 아니라 점포당 매출이다**
>
> 원천(추정매출-행정동, OA-22175)의 매출은 행정동 × 업종 × 분기 단위로 합산된 총액이다. 이를 그대로 예측하면 점포가 많은 동네일수록 값이 커져 '가게 하나가 얼마 버는가'와 어긋나고, 순위에서 점포 밀집 지역이 무조건 1등이 된다.
>
> 타깃 = sales_quarterly.amount ÷ store_quarterly.store_count (같은 행정동 · 업종 · 분기). store_count가 0이거나 없는 행은 학습에서 뺀다.
>
> 저장 · 계산 · 정렬은 분기 기준, 화면은 월 매출(분기 ÷ 3, 버림)로 표시한다(전체 명세 판정 31). '이 지역 해당 업종의 점포당 평균 매출 추정치'이며 개별 점포 매출 보장이 아님을 함께 적는다.

#### 5.2.2 피처

| 구분 | 피처 | 출처 |
|---|---|---|
| 업종 · 지역 | 업종 코드, 자치구 코드, 행정동 코드 | 마스터 (industry · dong) |
| 경쟁 환경 | 점포 수, 프랜차이즈 점포 수, 개업 수, 폐업 수 | store_quarterly (OA-22172) |
| 수요 | 유동인구 총계와 성별 · 연령대 · 시간대 분포 | population_quarterly (OA-22178) |
| 비용 | 자치구 ㎡당 월세 | district_rent |
| 시간 · 추세 | 분기(계절성), 직전 분기 · 전년 동기 점포당 매출, 성장세, 공간 기준 변경 플래그 | 파생 (5.2.5 · 5.4) |

- 소득소비(OA-22166)는 적재 표가 없어 1차 범위에서 뺀다(전체 명세 4.1 · 15장 20번). 표가 생기면 구매력 피처로 추가한다.
- 임대료는 자치구 단위라 같은 구 행정동끼리 값이 같다. 구 간 차이만 설명한다.

#### 5.2.3 알고리즘

| 구분 | 알고리즘 | 역할 |
|---|---|---|
| 기준선 ① | naive — 직전 분기 점포당 매출을 그대로 예측 | R²가 의미 있는지 판단하는 하한 (v0.9 추가) |
| 기준선 ② | 선형 회귀, RandomForest | 성능 하한선 확인 |
| 주력 | XGBoost `reg:quantileerror`, quantile_alpha 0.1 · 0.5 · 0.9 | 정형 데이터에서 안정적 성능, 결측 처리 용이. model_version xgb_v1 |
| 비교군 (2순위) | MLP (PyTorch) | 계획서의 딥러닝 비교 요구. 동일 분할 · 동일 피처, model_version mlp_v1 |

#### 5.2.4 전처리

- 매출 분포가 한쪽으로 치우치므로 타깃에 log1p 변환을 적용하고, 평가 지표는 원래 단위로 되돌려 보고한다.
- 최근 4개 분기 평균 점포 수가 5개 미만인 조합은 학습에서 제외하되, 예측은 만들어 적재하고 '표본 부족'으로 표시한다(판정 20).
- 업종 코드는 범주가 많아 순서형 또는 타깃 인코딩을 쓴다. 타깃 인코딩은 학습 분할 안에서만 통계를 계산해 누수를 막는다.

#### 5.2.5 데이터 기간과 분할 (확정 — 15장 13번)

> ⚠️ **2021년 이후 약 20개 분기, 2024년에 공간 기준 변경**
>
> 매출 · 유동인구는 2021년 이후 자료만 제공된다. 2024년부터 공간 기준이 표준단위구역으로 바뀌어 2023년과 2024년 사이 값이 같은 기준으로 이어지지 않는다. 무작위 분할은 쓰지 않는다. 같은 행정동의 인접 분기가 학습과 테스트에 동시에 들어가면 성능이 과대평가된다.

| 구분 | 결정 |
|---|---|
| 분할 | 분기 기준 시간 분할. **마지막 2개 분기 = 테스트, 그 앞 2개 분기 = 검증, 나머지 = 학습.** 최신 분기가 2025Q4라면 테스트 2025Q3~Q4, 검증 2025Q1~Q2, 학습 2021Q1~2024Q4. 실제 최신 분기가 달라도 '마지막 2 · 2' 규칙을 따른다 |
| 2024 처리 — 주 방식 | 전 기간으로 학습하고 공간 기준 변경 플래그(2024Q1 이후 = 1)를 넣는다. **경계를 넘는 시차 피처(2024Q1의 직전 분기, 2024Q1~Q4의 전년 동기)는 결측(NaN)으로 둔다.** 기준이 다른 값을 이어 붙이지 않으면서 표본은 최대한 쓴다 |
| 2024 처리 — 비교군 | 2024Q1 이후 분기만으로 학습한다(학습 4개 분기). 검증 pinball loss가 주 방식보다 낮으면 이쪽을 채택 |
| 평가 기준 | 검증 · 테스트가 모두 2024년 이후 기준이라 서비스가 실제로 쓰는 공간 기준으로 평가된다 |
| 최종 적재 | 하이퍼파라미터를 고정한 뒤 학습 + 검증 + 테스트 전체로 다시 학습해 전 조합을 예측한다. 보고하는 성능은 재학습 전 테스트셋 값이다 |

#### 5.2.6 예측 구간

분위수별로 학습한 세 값을 적재 전에 조합마다 정렬해 p10 ≤ p50 ≤ p90을 보장한다(CHECK 제약). 분위수 회귀는 시간이 흐른 구간에서 포함률이 모자라는 경향이 있으므로, **검증 분기의 잔차로 구간 폭을 보정(conformalized quantile regression)**한 뒤 테스트셋 포함률을 보고한다.

#### 5.2.7 평가 지표

| 지표 | 목표 | 용도 |
|---|---|---|
| R² (p50) | 0.6 이상 | 계획서 목표. 원 단위와 log 단위 둘 다 보고 |
| naive 대비 MAE 개선율 | 보고 | 직전 분기 값보다 얼마나 나은지. R²만으로는 모델 가치를 알 수 없다 (5.8) |
| MAE / MAPE | 참고 | 금액 오차 감각 확보, 화면 문구 근거 |
| 구간 포함률 · pinball loss | 80%에 근접 | 구간 신뢰성 검증 |

### 5.3 모델 B — 생존 기간 (XGBoost AFT)

#### 5.3.1 문제 정의

LOCALDATA 인허가의 개업일 · 폐업일로 점포의 영업 지속 기간을 모델링한다. 관측 시점까지 영업 중인 점포는 실제 영업 기간을 알 수 없으며(우측 절단), 이를 다루기 위해 일반 회귀가 아닌 생존 분석을 쓴다.

| 잘못된 접근 | 발생하는 문제 |
|---|---|
| 폐업한 점포만 학습 | 오래 버틴 점포가 빠져 생존 기간이 체계적으로 짧게 추정된다 |
| 영업 중 점포의 현재까지 기간을 정답으로 사용 | 끝나지 않은 기간을 최종값으로 간주해 역시 과소추정된다 |
| 영업 중 점포를 모두 제외 | 표본의 상당 부분이 사라지고 생존 편향이 남는다 |

#### 5.3.2 알고리즘

| 구분 | 알고리즘 | 특징 |
|---|---|---|
| 기준선 | 업종별 Kaplan–Meier 중앙값, Cox 비례위험 모형 (lifelines) | 위험 요인 설명. 비례위험 가정 검정 병행 |
| 주력 | XGBoost AFT (`survival:aft`) | 생존시간 분포를 직접 추정해 p10 · p50 · p90을 바로 산출. 모델 A와 라이브러리가 같다 |
| 선택 | Random Survival Forest (scikit-survival) | 여력이 있으면 C-index 비교용 |

AFT 설정: label_lower_bound = 영업기간(개월), label_upper_bound = 영업기간(폐업) 또는 +inf(영업 중). aft_loss_distribution(normal · logistic · extreme)과 scale은 검증셋으로 고른다. 분위수 q는 예측 위치값 μ에서 exp(μ + σ · z_q)로 계산한다.

#### 5.3.3 피처와 관측 기간 제약

피처는 점포의 **개업 분기 시점** 행정동 × 업종 상권 지표만 결합한다. 폐업 이후 정보를 넣으면 미래 정보를 미리 보는 것이 된다. 상권 지표가 2021년 이후뿐이므로 학습 표본은 2021년 이후 개업 점포로 한정되고 관측 기간은 최대 약 60개월이다. 관측 종료일은 원천 추출일로 둔다(가정).

전 조합 예측은 각 행정동 × 업종에 대해 최신 기준 분기의 상권 지표로 '지금 개업하는 점포'를 가정해 계산한다.

#### 5.3.4 분할 (확정 — 15장 13번)

| 구분 | 개업 분기 |
|---|---|
| 학습 | 2021Q1 ~ 2022Q4 |
| 검증 | 2023Q1 ~ 2023Q4 (분포 · scale 선택) |
| 테스트 | 2024Q1 이후 |

테스트 점포는 관측 기간이 짧아 절단 비율이 높다. 그래서 C-index는 절단을 고려한 Uno C를 함께 보고한다. 최종 적재 전에는 전 기간으로 다시 학습한다.

#### 5.3.5 출력과 표기 (확정 — 15장 3번)

| 항목 | 결정 |
|---|---|
| 주 출력 | 생존기간 개월 p10 · p50 · p90 (전체 명세 판정 6). prediction의 survival_p10 · p50 · p90 |
| 1년 · 3년 생존확률 | 같은 AFT 분포에서 S(12) · S(36)을 추가 비용 없이 계산할 수 있다. **2순위로 prediction에 보조 칼럼(survival_prob_12m · survival_prob_36m) 추가를 제안**한다. DB 변경이라 백엔드와 합의 후 반영. 1순위 화면에는 넣지 않는다 (권고) |
| 외삽 표기 | 관측 한계 60개월을 넘는 값은 외삽이다. 화면에서 p90이 60을 넘으면 '60개월 이상'으로 표기할 것을 권한다 (권고, 프론트) |
| 순위 영향 | AFT는 모든 조합이 같은 σ를 쓰므로 어느 분위수로 정렬해도 순서가 μ 순서와 같다. survival_p50이 외삽이어도 **생존 백분위는 흔들리지 않는다** |

#### 5.3.6 평가

| 항목 | 내용 |
|---|---|
| 주 평가 지표 | Harrell C-index 0.7 이상 (계획서 목표), 하한 0.65 (5.8) |
| 함께 보고 | 업종 내 C-index 평균, Uno C, 시간 의존 AUC(12 · 36개월), 통합 Brier score |
| 구간 | 절단을 고려한 p10~p90 포함률 |
| 화면 표기 | '이 지역 · 업종의 예상 생존기간 추정치'로 표기, 개별 점포 보장 아님을 명시 |

### 5.4 성장세 지표 (전체 명세 판정 7)

이미 확보한 매출 시계열에서 계산하는 파생 지표다. 현재 수치는 평범하지만 상승 중인 지역이 순위에 반영되게 한다.

```
growth_rate(dong, industry) =
    Σ 최근 4분기 점포당 매출 ÷ Σ 직전 4분기 점포당 매출 − 1

# 두 구간 모두 2024Q1 이후 분기만 쓴다 (공간 기준 경계를 넘지 않음)
# 경계 이후 확보 분기 k ≥ 8 → growth_confidence '높음'
# 4 ≤ k < 8 → '낮음' (계산 방식은 아래 권고)
# k < 4 → NULL (화면 '데이터 없음')
```

> 💡 **k가 4~7일 때의 계산 (권고)**
>
> 전체 명세 6.4는 ⌊k/2⌋ 분기씩 나눠 비교한다. k가 6이면 3개 분기끼리 비교하게 되는데, 두 구간의 분기 구성이 달라(예: Q1~Q3 vs Q4~Q2) 계절성이 상쇄되지 않는다.
>
> 대신 최근 (k − 4)개 분기를 1년 전 같은 분기와 비교하는 것을 권한다. 분기 구성이 같아 계절성이 상쇄된다. 최신 분기가 2025Q4이면 k = 8이라 1차 적재에는 영향이 없다.

### 5.5 전 조합 일괄 예측과 종합점수 선계산

학습이 끝나면 행정동 426 × 업종 100 = 42,600개 조합 전체를 예측하고, 같은 배치에서 종합점수까지 계산해 한 번에 적재한다. 요청 시에는 조회만 한다.

```
1. 모델 A · B로 전 조합 예측 → 분위수 교차 보정(정렬)
2. 성장세 계산 (5.4)
3. 같은 industry_code · model_version 안에서 PERCENT_RANK
     sales_percentile    ← sales_p50
     survival_percentile ← survival_p50
     growth_percentile   ← growth_rate      (NULL은 모집단에서 제외)
4. total_score = round(100 × Σ w'(i) × p(i), 1)
     w = 매출 0.4 · 생존 0.4 · 성장세 0.2, 값이 없는 항목은 빼고 비례 재배분
5. score_rank = 같은 업종 · 모델 안 total_score 순위 (동률은 dong_code 오름차순)
6. 스테이징 표에 적재 → 한 트랜잭션에서 교체, 해당 summary_cache 행 삭제
```

| 칼럼 | 내용 |
|---|---|
| dong_code, industry_code, model_version | 키 (PK) |
| sales_p10 · p50 · p90 | 점포당 분기 매출 80% 구간과 중앙값 (원) |
| survival_p10 · p50 · p90 | 생존기간 80% 구간과 중앙값 (개월, 소수 1자리) |
| growth_rate · growth_confidence | 성장세 (산출 불가 시 null) |
| sales · survival · growth_percentile, total_score, score_rank | 선계산 점수 (v1.6 판정 30) |
| computed_at | 적재 시각 |

#### 검토 결론 — 선계산 구조는 채택, 단 5가지 조건

| No | 조건 | 이유 · 처리 |
|:---:|---|---|
| 1 | 점수는 prediction 재적재와 **같은 트랜잭션**에서만 갱신한다 | 예측값과 점수가 다른 시점 값이 되면 근거 분해가 맞지 않는다. 전체 명세 4.6의 표 교체 규칙을 그대로 쓴다 |
| 2 | 백분위 모집단에 '표본 부족' 행을 포함한다 | 판정 20과 일관. 예측값은 원천 값이 아니라 모델 출력이라 소표본 노이즈가 직접 들어가지는 않는다. 다만 검증 때 표본 부족 행의 점수 분포가 상위에 몰리지 않는지 점검한다 |
| 3 | 성장세 결측 비율을 감시한다 | 재배분 때문에 행마다 가중치가 다르면(50 · 50 vs 40 · 40 · 20) 점수 척도가 조금씩 달라진다. 1차는 성장세가 전부 null이라 문제없다. 성장세 도입 후 null 비율이 20%를 넘으면 null을 0.5(업종 중앙)로 두는 방식과 비교한다 (권고) |
| 4 | data_status(표본 부족)도 prediction에 선계산한다 | 전체 명세 7.6 4단계는 요청 때 store_quarterly를 집계한다. 이 값도 요청과 무관하므로 칼럼으로 두면 ⑱ 랭킹(426행)과 추천이 같은 판정을 쓰고 응답이 가벼워진다 (권고, DB 변경 — 백엔드 합의) |
| 5 | prediction에 학습 원천의 최신 분기를 남긴다 | 지금은 computed_at과 model_version뿐이라 어느 분기 데이터로 만든 예측인지 알 수 없다. source_quarter(예: 20254) 칼럼을 두고, run_weekly의 재생성 판단도 이 값과 원천 최신 분기를 비교하게 한다 (권고, DB 변경 — 백엔드 합의) |

### 5.6 LLM 사용 범위 (확정 — 15장 12번)

LLM은 숫자를 만들지 않는다. 비정형 공고문을 정리하고, 서버가 계산한 값을 문장으로 옮기고, 자격증 이름을 표준 목록에 맞추는 일만 한다. 요약문과 화면 수치가 어긋나면 화면 수치가 정본이다. 호출부는 인터페이스로 감싸 모델을 바꿀 수 있게 둔다.

#### 5.6.1 LLM ① — 지원사업 공고 구조화 (배치 · 주 1회)

| 항목 | 결정 |
|---|---|
| 모델 | `claude-opus-5-5` (정확도 우선. 잘못 추출한 금액은 사용자 예산에 그대로 들어간다) |
| 출력 강제 | 구조화 출력(`output_config.format`, JSON 스키마). 스키마는 전체 명세 4.8의 필드(name · agency · amount_max · district_code · is_exclusive · apply_start · apply_end · eligibility · source_url) |
| 호출 방식 | Message Batches API — 비동기, 요금 50% 할인. 주 1회 배치라 지연이 문제되지 않는다 |
| 검수 | verified_by가 기록된 행만 매칭. 모호한 요건은 판단보류로 남겨 매칭에서 뺀다 |

#### 5.6.2 LLM ② — 행정동 × 업종 요약 (배치 · 기준 분기 변경 시)

| 항목 | 결정 |
|---|---|
| 생성 범위 | prediction에 행이 있고 **data_status 정상 · 최근 4개 분기 평균 점포 5개 이상**인 조합만. 최대 42,600개 중 약 2만 개로 가정(적재 후 실제 수 확정) |
| 입력 | 서버가 계산한 지표(업종 분포 · 매출 추이 · 임대료 · 예측 구간 · 성장세 · 유동인구)를 변수로 넣는다. 사용자별 예산은 넣지 않는다 |
| 모델 | 기본 `claude-opus-5-5`. 표본 50건을 모델별로 생성해 사실 오류 · 문장 품질을 비교한 뒤, 팀이 더 싼 모델로 내릴지 결정한다 (비용 비교는 5.6.4) |
| 호출 방식 | Message Batches API + 공통 지시문 프롬프트 캐싱 |
| 릴리스 | 1순위(중간발표)에서는 생성하지 않는다. summary_text가 null이면 프론트 템플릿으로 대체되므로 화면은 성립한다 |

#### 5.6.3 LLM ③ — 자격증 정규화 폴백 (요청 시)

| 항목 | 결정 |
|---|---|
| 호출 조건 | common/certificate_normalizer 동의어 사전에 없을 때만 |
| 출력 | 표준 자격증 목록 중 하나 또는 '없음'(구조화 출력, enum) |
| 제한 | 타임아웃 2초, 재시도 없음. 실패 · 타임아웃 · '없음'이면 원문 그대로 진행 |
| 모델 | **2초 안에 끝나는지 실측한 뒤 확정.** 후보는 `claude-opus-5-5`(effort low)와 더 빠른 소형 모델. p95 지연이 2초 안에 들어오기 전까지는 폴백을 끄는 설정 플래그를 둔다 |
| 빈도 줄이기 | 폴백 로그의 원문을 모아 동의어 사전을 주기적으로 보강한다 |

### 5.7 딥러닝을 주력으로 두지 않는 이유

- 데이터가 정형 표이고 규모가 수만 행 수준이다. 이 조건에서는 트리 앙상블이 심층 신경망보다 안정적인 성능을 내는 것이 일반적이다.
- 추천 근거를 항목별로 설명해야 하므로 기여도 해석이 쉬운 모델이 유리하다.
- 계획서의 딥러닝 비교 요구는 동일 분할 · 동일 피처로 MLP를 학습해 수치로 비교하는 실험으로 충족한다(mlp_v1을 prediction에 나란히 저장).

### 5.8 성능 목표와 검증 — 현실성 검토

| 항목 | 목표 | 현실성 | 조치 |
|---|---|---|---|
| 매출 예측 R² (p50) | 0.6 이상 | **너무 쉽다.** 직전 분기 매출이 피처에 있으면 naive 예측만으로도 0.6을 넘을 가능성이 크다. 목표를 달성해도 모델의 가치를 말해주지 못한다 | 목표는 유지하되 **naive 대비 MAE 개선율**을 함께 보고하고, 원 단위 · log 단위 R²를 모두 적는다 |
| 생존 C-index | 0.7 이상 | **도전적이다.** 피처가 행정동 × 업종 단위라 같은 칸 · 같은 분기에 개업한 점포끼리는 구분할 수 없다. 업종 간 차이가 커서 전체 C는 0.7 근처가 가능하지만 업종 내 C는 0.6 안팎으로 예상한다(가정) | 목표 0.7 유지, **하한 0.65** 명시. 업종 내 C를 별도로 보고. LOCALDATA의 점포 단위 필드(시설 면적 등)를 피처로 검토하되, 전 조합 예측 때는 기준값(희망 면적 33㎡)을 넣어야 한다 |
| 예측 구간 포함률 | 80%에 근접 | 보정 없이는 시간 이동으로 모자랄 수 있다 | 검증 분기 기반 구간 보정(5.2.6) 후 측정하면 현실적 |
| 지원사업 추출 정확도 | 무작위 30건 · 필드 일치율 85% | 판단보류 행을 빼고 재면 현실적 | 백엔드 측정 (v_extraction_accuracy) |
| 지원사업 매칭 정확도 | 테스트 케이스 정합 | 규칙 판정이라 테스트로 보장 가능 | tests/test_evaluator |
| 응답 속도 | 1초 이내 | 점수 선계산으로 여유가 크다 | 자격증 폴백이 걸린 요청만 최대 2초 (5.6.3) |

계획서 성능 목표 표의 '창업 예측 모델 정확도'는 매출 예측 모델을 가리키는 것으로 보고 '매출 예측 정확도'로 명칭을 정리했다. 응답 목표는 계획서의 10초에서 팀 원칙인 1초로 강화했다.

### 5.9 전체 명세 v1.6 판정 검토 의견 (AI 파트)

| 판정 | 내용 | 의견 |
|:---:|---|---|
| 1 | 백분위 40 · 40 · 20, 결측 재배분, 예산 여유는 점수 제외 | **동의.** 예산 여유는 자치구 단위 추정치라 점수에 넣으면 추정 오차가 전체 순위로 번진다 |
| 6 | 생존 출력 개월 p10 · p50 · p90 | **동의.** 60개월 초과 표기와 S(12) · S(36) 보조 칼럼 제안(5.3.5) |
| 7 | 성장세 = 최근 4분기 합 ÷ 직전 4분기 합 − 1 | **동의.** k가 4~7일 때의 계산만 전년 동기 비교로 바꾸자는 권고(5.4) |
| 8 | 매출 타깃 점포당 (가정) | **확정**(15장 2번) |
| 9 | 요약은 배치 생성, 요청 경로 LLM 없음 | **동의.** 캐시 미스는 null + 템플릿. 요청 경로 예외는 자격증 폴백 하나(판정 12) |
| 20 | 표본 부족 조합도 순위에 포함 | **동의.** 점수 분포 점검 조건(5.5 조건 2) |
| 22 | 백분위 모집단 = 서울 전체 행정동 | **동의.** 같은 동이 조건마다 다른 점수를 받지 않고, 선계산이 가능해지는 근거다 |
| 30 | 백분위 · 종합점수 배치 선계산 | **동의.** 5.5의 조건 5가지를 붙인다 |

전체 명세 7.6~7.9에 대한 의견:

- **7.6 후보 선정** — 4단계 표본 판정을 요청 때 하지 말고 prediction에 선계산하자(5.5 조건 4).
- **7.7 백분위** — PERCENT_RANK · 동률 같은 값 · N = 1이면 1.0 모두 동의. 근거 분해의 '상위 N%' = (1 − 백분위) × 100 올림도 동의.
- **7.8 정렬 탭** — 동의. 생존순은 survival_p50으로 정렬해도 AFT 특성상 μ 순서와 같다(5.3.5).
- **7.9 요약 템플릿** — [예측] 문장이 '점포당 분기 매출'로 되어 있는데 화면은 월 매출(판정 31)이다. 템플릿도 월 매출로 맞추자(프론트).

### 6.3 행정동 임대료 추정 (2순위 — 향후 과제)

전체 명세 판정 5로 1차는 자치구 단위 임대료(district_rent 25행)를 쓴다. 아래는 행정동 해상도로 내려갈 때의 경로로, v0.3 · v0.5의 검토 기록이다.

| 검토한 방법 | 결과 |
|---|---|
| 부동산원 상가 임대료 단독 사용 | 소규모상가 표본이 전국 5,526동 · 232개 상권뿐이라 행정동 단위로 내려갈 수 없다 |
| 상권 지표로 임대료를 회귀 추정 | 임대료가 매출 · 생존 모델의 피처로도 쓰여 순환 참조가 된다 (팀 v0.3에서 불가 판정) |
| 개별공시지가 + 부동산원 단가 결합 | 공시지가는 전 필지를 덮으므로 행정동 해상도가 나온다. 금액 수준은 부동산원 단가로 맞춘다 |

```
1. 용도지역으로 상업 · 근린 용도 필지만 남긴다
2. 행정동별 공시지가 중앙값 → 자치구 평균 대비 배율
3. 배율 × 자치구 임대료 → 행정동 추정 월세 · 보증금
```

### 7.2 2단계 API 흐름

추천은 두 번의 요청으로 나뉜다. 먼저 가용 예산을 보여주고, 사용자가 확인한 뒤 추천을 받는다. 가용 예산 화면은 기능명세서 2.3.1(필수 경유 스텝)에 해당한다.

| 단계 | API | 입력 | 처리 | 출력 |
|:---:|---|---|---|---|
| 1 | calculate-budgets | 나이 · 자격증 · 경력 · 자본금 · 업종 | common/evaluator로 지원사업 판정 → common/budget로 자치구별 합산 → 스냅샷 저장 | rec_id, 자치구 25개별 가용예산 · 예산 여유 · passed, 매칭된 사업 목록 |
| 2 | recommendations | rec_id | 스냅샷의 통과 · 확인불가 자치구 행정동 → prediction의 선계산 점수 조회 → 정렬 | 추천 행정동 순위, 항목별 근거, 요약(캐시) |

### 7.3 가용 예산 — 보수와 기대 (v0.5 권고 기록, 미채택)

> ⚠️ **'받을 수 있는 금액'이 부풀려지지 않게 한다**
>
> 창업 지원사업의 상당수는 요건만 맞으면 받는 돈이 아니라 경쟁을 거쳐 선정된다(예: 청년창업사관학교). 자격 충족을 곧 수령으로 계산하면 가용 예산이 실제보다 커진다.
>
> 융자는 갚아야 하는 돈이고, 공간 · 교육 지원은 현금이 아니다. 이들을 보조금과 같은 '금액'으로 더하면 안 된다.
>
> 보수 예산 = 자본금 + (자동 지급 · 보조금). 기대 예산 = 보수 + (경쟁 선정 · 보조금). 융자는 별도 표시, 현물 지원은 초기비용 차감 항목으로 처리한다.
>
> 필터는 기대 예산으로 하고, 각 추천 행정동에 보수 예산 기준 통과 여부를 함께 표시한다.

```
보수[gu] = 자본금 + Σ amount_max   (자격 충족 ∧ selection=자동 ∧ type=보조금 ∧ 해당 구 적용)
기대[gu] = 보수[gu] + Σ amount_max (자격 충족 ∧ selection=경쟁 ∧ type=보조금 ∧ 해당 구 적용)
중복 수혜 불가 사업끼리는 금액이 큰 쪽만 합산
```

### 7.4 예산 필터 (v0.5 권고 기록 — 확정안은 전체 명세 7.5)

```
여유[dong] = 기대[gu(dong)] - initial_cost[dong]        # gu(dong) = dong_code 앞 5자리
통과 조건 : 여유[dong] >= 0
보수 통과 : 보수[gu(dong)] - initial_cost[dong] >= 0    # 결과 배지로 표시

initial_cost = deposit + monthly_rent × 예비개월(기본 6) + 업종 평균 시설비   (가정)
```

확정안: 추정 임대비용 = 월세 × (15 + 3), 월세 = rent_per_sqm × 1,000 × 희망 면적(기본 33㎡). 자치구 단위 값이고 결측(도봉구)은 '확인불가'로 후보에 남긴다.

### 7.5 순위 산정 (v0.9 — 전체 명세 v1.6 7.7 기준)

```
p(i)        = 같은 업종 · 같은 model_version의 서울 전체 행정동 안 PERCENT_RANK
              i ∈ {sales_p50, survival_p50, growth_rate},  NULL은 모집단에서 제외
w           = 매출 0.4 · 생존 0.4 · 성장세 0.2
w'(i)       = w(i) ÷ Σ w(값이 있는 지표)
total_score = round(100 × Σ w'(i) × p(i), 1)
근거 분해    : 항목별 기여도 = w'(i) × p(i) × 100 (합 = total_score)

계산 위치    : 배치가 prediction 적재 때 선계산 (5.5). 요청 경로는 읽기만
1순위 릴리스 : 성장세가 전부 NULL → 재배분으로 자동 매출 50 · 생존 50
```

예산 여유는 점수에 넣지 않고 값만 표시한다(판정 1 · 14). v0.5의 후보 집합 안 min-max · 여유율 포함 방식은 미채택(5.10).

|---|---|---|
| 지원사업 판정 · 예산 합산 | 100ms 이내 | 수백 행 조회 + 비교 연산, 25회 반복 |

- 직접 찾아보기: 조건 없이 행정동을 검색하거나 업종별 랭킹 지도에서 골라 상권 상세로 이동한다.
- 상권 상세: 업종 분포, 추정 임대료, 매출 추이, 예측 구간, 종합점수, 요약 캐시의 요약문을 보여준다.
- 상권 비교: 1~4개 행정동을 같은 축으로 나란히 비교한다.
- 대시보드: 브라우저 localStorage에 저장된 최근 추천과 즐겨찾기를 보여준다. 기기 · 브라우저가 바뀌면 보이지 않는다.

## 10. 배포 및 인프라

### 10.1 환경 구성

| 구성 요소 | 로컬 개발 | 운영 |
|---|---|---|
| DB | docker-compose의 PostgreSQL 컨테이너 | RDS 또는 EC2 내 컨테이너 (확인 필요) |
| API | docker-compose의 api 컨테이너 | ECR 이미지 → EC2 컨테이너 |
| 웹 | docker-compose의 web (Vite 개발 서버) | Vercel 정적 배포 |
| 배치 | docker compose run batch ... | EC2 cron이 배치 컨테이너 실행 |
| 모델 파일 | 배치 내부에서만 사용 | API 이미지에 포함하지 않음 (예측표만 조회) |

### 10.2 CI/CD

- CI: PR과 push 시 common · api · batch 테스트와 린트를 실행한다. common은 배치와 API 양쪽이 쓰므로 테스트 우선순위가 가장 높다.
- 배포: 초기에는 수동 실행으로 두고, 인프라 · 시크릿 구성이 끝나면 main push 시 자동 배포로 전환한다.
- 이미지 태그를 버전으로 관리해 실패 시 이전 이미지로 되돌린다.

### 10.3 파이프라인 전환 결과 (2026.09.26 완료)

| 항목 | 이전 (Spring) | 현재 (FastAPI) |
|---|---|---|
| Dockerfile | JRE 이미지 + jar 실행 | python 슬림 + uvicorn (api) / 학습 의존성 포함 별도 이미지 (batch) |
| CI | JDK 21 + Gradle build | Python 3.11 + ruff + pytest |
| 설정 주입 | application-*.yml을 시크릿에서 복원 | 환경변수 주입, .env는 저장소에 두지 않음 |
| 이미지 태그 | latest | latest + 커밋 SHA (롤백용) |
| 포트 | 8080 | 8000 |
| 유지 | ECR 인증, EC2 IAM Role, 시크릿, PR 라벨링 | 그대로 재사용 |

CI는 배치 의존성(xgboost · scikit-survival)을 설치하지 않는다. 설치가 무거워 common과 api 테스트만 돌리며, 배치 작업이 붙으면 별도 job으로 분리한다. 도커 이미지 빌드는 아직 로컬에서 확인하지 못했다. (확인 필요)

### 10.4 설정과 비밀 관리

- DB 접속 정보, LLM API 키, 공공데이터 인증키는 저장소에 두지 않고 GitHub Secrets → 환경변수로 주입한다.
- LLM 키는 배치(공고 구조화 · 요약 생성)와 API(자격증 자유 입력의 LLM 폴백) 모두에 주입한다. 프론트에는 내려보내지 않는다(전체 명세 v1.6 13장 판정 12).
- CORS 허용 도메인은 Vercel 배포 주소가 확정되면 설정한다.

| 구분 | 리스크 | 영향 | 대응 |
