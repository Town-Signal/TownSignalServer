## 설계서 v1.5 — 3대 원칙

- **2단 분리** — 배치가 support_program · district_rent · prediction 세 표를 미리 채움. 요청 시에는 조회와 사칙연산만 하므로 1초 이내 응답. **모델 서빙 서버 없음**
- **동기식 + common 공유** — async를 쓰지 않음. 자격요건 평가기와 예산 로직을 배치와 API가 같은 모듈로 공유해 로직 불일치를 차단함
- **Redis 배제** — LLM 요약은 summary_cache 테이블로 충분. 인프라 하나 늘리면 팀원 5명이 각자 띄워야 함

> ⚠️ **v0.6 조정 — 배치 주기를 나눈다**
>
> cron은 주 1회로 두되, 매주 다시 만드는 것은 지원사업표뿐이다. 임대료표 · 예측표 · 요약 캐시는 원천(상권 · 인구)이 분기 갱신이라 **기준 분기가 바뀐 주에만** 재생성한다. 매주 재학습해도 값은 그대로인데 학습 비용만 든다.

## 저장소 구성

| 저장소 | 내용 | 담당 |
| --- | --- | --- |
| **TownSignalServer** | 파이썬 전부 — api · batch · common · data | 박규민 · 노현석 · 노승민 · 이성진 |
| **TownSignalFE** | React SPA | 한석희 |
| TownSignalAI | 비어 있음. batch로 흡수됨 → 보관 처리 예정 | — |

```
TownSignalServer/
├── api/          # FastAPI 동기식. DTO는 api/schemas/에만   ← common import
├── batch/        # 수집 · 전처리 · 학습 · 표 생성            ← common import
│   └── jobs/     # python -m batch.jobs.<작업명> 으로 실행
├── common/       # evaluator · budget · scoring · constants (Pydantic 없음)
├── data/         # raw · processed · seed   → 데이터 파이프라인 페이지
├── tests/
├── Dockerfile          # api 이미지
├── Dockerfile.batch    # batch 이미지
└── docker-compose.yml
```

**프론트는 합치지 않는다.** `common/`을 공유해야 하는 건 파이썬 쪽(api · batch)뿐이다. 프론트는 툴체인(Node/Vite)과 배포 대상(Vercel)이 달라, 합치면 CI에 경로 필터만 늘어난다. 나눠두면 전부 파이썬이라 테스트를 그냥 다 돌리면 된다.

**이미지를 둘로 나눈다.** 예측을 요청 때 계산하지 않고 prediction 표에서 읽기 때문에 **API 이미지에는 xgboost · scikit-survival이 필요 없다.** 배치만 학습 의존성을 가진다. API는 모델 파일을 로드하지 않는다.

## 왜 두 덩어리로 나뉘는가

이 서비스에서 헷갈리는 지점은 하나이다. **어떤 일이 미리 끝나 있고, 어떤 일이 사용자 요청 때 일어나는가.** 계획서는 기술 나열과 기능 나열이 섞여 있어 이 구분이 보이지 않는다.

어려운 계산은 전부 ①에서 끝나 있고, 사용자 요청(②)은 만들어둔 표를 조회해 더하고 빼는 일만 한다. 계획서의 "응답 10초 이내"는 이 구조에서 **1초 이내**로 줄어든다.

요청 시에 새로 계산하는 값은 **가용예산 · 여유 · 점수 세 가지뿐**이다. 나머지는 전부 조회다.

## ① 배치 — 미리 만들어두는 표

프로젝트의 **약 80%가 여기에 있다.** 사용자가 오기 전에 완성돼 있어야 한다.

| 표 | 크기 | 내용 | 만드는 법 | 담당 · 주기 |
| --- | --- | --- | --- | --- |
| **지원사업표** `support_program` | 수백 행 | 사업명 · 나이/경력/자격증 조건 · 금액 · 적용 자치구 · 중복수혜 여부 · **지원 유형(보조금/융자/현물)** · **선정 방식(자동/경쟁)** | 공고문을 LLM으로 구조화 → 원문과 대조해 사람이 검증. `verified`만 매칭에 사용 | 백엔드 (박규민·노현석) · 주 1회 |
| **임대료표** `district_rent` | 426행 | 행정동별 보증금 · 월세 · **초기비용** 추정 | 공시지가로 행정동 상대지수 → 상가 임대료 단가로 금액 보정 | 데이터 (노승민) · 분기 1회 |
| **예측표** `prediction` | 42,600행 | 행정동 426 × 업종 100. **점포당** 분기매출(구간) · 1년/3년 생존확률 · 성장세 · 표본 플래그 · 모델 버전 | 과거 매출·유동인구·점포수로 학습 → 전 조합 예측해 적재 | AI (이성진) · 분기 1회 |
| 요약 캐시 `summary_cache` | 426행 | 행정동 상세 요약문 (상권 상세 화면용) | 배치에서 LLM으로 사전 생성 | AI (이성진) · 분기 1회 |

**매출은 점포당으로 잡는다.** 원천(OA-22175)의 매출은 행정동 × 업종 총액이라 그대로 예측하면 점포가 많은 동네가 무조건 1등이 된다. 타깃 = 분기 매출 ÷ 점포 수(OA-22172와 결합). → 5.2절

**생존기간은 생존분석으로 한다.** 아직 영업 중인 가게는 실제 영업 기간을 모르는 상태(우측 절단)라 일반 회귀로 풀면 생존 기간이 짧게 추정된다. 상권 피처가 2021년 이후뿐이라 출력은 1년 · 3년 생존확률로 한정한다. → 5.3절

## ② 요청 시 — 사용자가 버튼 누를 때

새로 계산하는 게 거의 없다. 아래는 **27세 · 자본금 3,000만원 · 조리기능사 보유 · 요식업 희망**이 들어왔을 때 일어나는 일이다. (수치는 설명용 가상값)

1. **조건 입력** — 나이 27 / 자본금 30,000,000 / 경력 0년 / 업종 요식업 / 자격증 조리기능사
2. **지원사업표와 대조** — 청년창업사관학교 20,000,000(전국 · **경쟁 선정**) · 관악구 청년창업지원금 5,000,000(관악구 한정)
3. **자치구별 가용예산 산출** — 구마다 다르다는 것이 이 서비스의 핵심

| 자치구 | 보수 (자본금 + 선정 절차 없는 지원) | 기대 (경쟁 선정 성공 가정) |
| --- | --- | --- |
| 관악구 | 30,000,000 | 55,000,000 |
| 강남구 | 30,000,000 | 50,000,000 |

4. **임대료표와 비교해 감당 못 할 곳 제거** — 여유 = 가용예산 − 초기비용

| 행정동 | 초기비용 | 기대 기준 | 보수 기준 |
| --- | --- | --- | --- |
| 신림동 (관악구) | 40,000,000 | +15,000,000 통과 | −10,000,000 선정 필요 |
| 역삼동 (강남구) | 120,000,000 | −70,000,000 탈락 | — |

5. **예측표에서 남은 동네를 꺼내 정렬 + 요약** — 점포당 매출 · 생존확률 · 여유율 · 성장세로 순위 → 템플릿 요약문 생성

→ **추천 행정동 순위 + 추천 근거**

### 왜 '받을 수 있는 금액'을 둘로 나누는가

창업 지원사업의 상당수는 요건만 맞으면 받는 돈이 아니라 **경쟁해서 선정**된다(청년창업사관학교가 그렇다). 자격 충족을 곧 수령으로 계산하면 가용예산이 실제보다 커지고, 추천 결과 전체의 신뢰가 무너진다. 융자는 갚아야 하는 돈이고 공간 · 교육 지원은 현금이 아니므로 보조금과 같이 더하면 안 된다.

필터는 기대 기준으로 하되, 각 추천 동에 **보수 기준 통과 여부를 배지로 함께 표시**한다. 지원금이 선택지를 넓힌다는 차별점은 살리면서, 어떤 결과가 선정을 전제로 하는지 사용자가 알 수 있다. → 7.3절

### 요청 시에는 LLM을 부르지 않는다

LLM 호출은 보통 몇 초가 걸려 1초 원칙과 충돌한다. summary_cache는 같은 요청이 두 번째 올 때부터만 도움이 되고, 추천 요약은 사용자마다 예산 맥락이 달라 미리 만들어둘 수도 없다.

- **추천 결과 요약** → 계산값을 문장 틀에 채우는 **템플릿** (LLM 없음)
- **행정동 상세 요약** → 배치에서 426건 사전 생성 → summary_cache 조회
- **지원사업 공고 구조화** → 배치 · 주 1회

→ 5.6절

임대료 대안으로 부동산원 상가 임대료를 검토했으나, **소규모상가 표본이 전국 5,526동·232개 상권뿐**이라 행정동 단위로는 원리상 내려갈 수 없다. 행정동 해상도가 필요하면 전 필지를 덮는 개별공시지가와 결합하는 수밖에 없다. 임대료를 상권 지표로 회귀 추정하는 방식은 임대료가 다시 매출 · 생존 모델의 피처로 쓰이므로 **순환 참조**가 되어 불가(v0.3 판정).

추가로 두 가지. 매출·유동인구 모두 **2021년 이후 자료만** 제공되고(20개 분기), **2024년부터 공간 기준이 표준단위구역으로 바뀌었다.** 성장세 지표를 계산할 때 2023↔2024 경계를 그냥 이어 붙이면 안 된다. 경계 이후 분기끼리 비교가 가능해지는 **2025년 1분기부터** 성장세를 산출한다.

| **이성진** | 예측표 — 모델 학습 후 42,600행 채우기(생존분석 포함). 요약 캐시. |
| **박규민 · 노현석** | 지원사업표 + ② 전체 계산 로직(common · api). 공고 수집은 상권 데이터와 독립이라 **지금 바로 병렬 착수 가능**. |
| **한석희** | 화면 6~9개. 명세서에 빠져 있는 **"가용예산 결과 화면"**과 단계별 로딩 화면이 추가로 필요하다. |

> ⚠️ 지금 팀의 유일한 구조적 위험은 **데이터 통합이 끝날 때까지 나머지 넷이 대기하는 것**이다. 지원사업표는 상권 데이터와 무관하므로, 대기 인력을 그쪽에 붙이면 병목이 풀린다. 게다가 상권 분석은 이미 골목상권이 하고 있지만 **지원사업 구조화는 아무도 안 했다** — 차별점도 그쪽에 있다.

## 2. 서비스 개요

### 2.1 서비스 정의

> 💡 **정의**
>
> 서울 청년 예비창업자가 인적 조건과 자본금을 입력하면, 받을 수 있는 창업 지원금을 반영한 자치구별 가용 예산을 계산하고, 그 예산으로 감당 가능한 창업 후보 행정동을 예상 매출 · 생존 가능성 순으로 추천하는 웹 서비스.

### 2.2 대상 사용자

서울에서 창업을 준비하지만 위치를 정하지 못한 만 39세 이하 예비창업자. 업종은 대략 정했으나, 자신이 어떤 지원사업에 해당하는지, 그래서 실제로 쓸 수 있는 돈이 얼마인지, 그 돈으로 어느 동네에 들어갈 수 있는지를 한 번에 파악하지 못한다.

### 2.3 해결하려는 문제

| 사용자가 겪는 문제 | 현재 상황 | 본 서비스의 해결 |
|---|---|---|
| 받을 수 있는 지원금을 모른다 | 공고가 기관별로 흩어져 있고 요건이 제각각 | 인적 조건을 요건과 규칙 기반으로 매칭해 금액 산출 |
| 지원금이 어느 동네를 의미하는지 모른다 | 지원사업 검색과 상권분석이 분리되어 이중 작업 | 가용 예산에서 초기비용을 빼 감당 가능한 지역만 남김 |
| 어디서 시작할지 모른다 | 기존 상권분석은 위치를 이미 정했다는 전제 | 조건만 입력하면 후보 행정동을 역으로 추천 |
| 얼마나 벌고 버틸지 모른다 | 현재 지표만 조회 가능 | 점포당 예상 매출과 생존 확률을 구간으로 제시 |

### 2.4 경쟁 서비스와의 차이

| 서비스 | 제공 방식 | 본 서비스와 겹치지 않는 지점 |
|---|---|---|
| 소상공인365 | 위치 지정 후 매출 · 유동인구 등 현재 지표 조회 | 예산 입력이 없고 지원사업은 안내 수준 |
| 서울시 골목상권 분석 | 행정동 · 업종 선택 후 조회, 매출 증감 자동 코멘트 | 조회는 정교하나 지원금 계산 · 지역 역추천은 없음 |
| 리치고 · 부동산지인 | 인구 · 공급 기반 주택 가격 예측 | 주거용 부동산 전용, 상권 · 창업은 다루지 않음 |
| K-Startup · 청년몽땅정보통 | 청년 창업 지원사업 공고 제공 | 공고만 제공, 상권분석과 연결되지 않음 |

상권 분석은 이미 골목상권이 정교하게 하고 있지만, **지원사업을 구조화해 예산으로 환산하는 일은 아무도 하지 않았다.** 차별점은 그쪽에 있다. 기존 서비스가 '이 동네가 어떤가'에 답한다면, 본 서비스는 '내 조건과 받을 수 있는 돈을 감안하면 어디가 유리한가'에 답한다.

### 2.5 MVP 범위

| 구분 | 포함 | 제외 (향후 과제) |
|---|---|---|
| 지역 | 서울 25개 자치구 · 426개 행정동 | 수도권 및 기타 광역시 |
| 사용자 | 청년 예비창업자 (지원사업 요건 기준) | 기존 사업자 이전 · 확장, 주거 입주자 관점 |
| 업종 | 서울시 상권분석서비스 업종 약 100개 | 프랜차이즈 브랜드 단위 분석 |
| 기능 | 지원금 계산, 지역 추천, 매출 · 생존 예측 조회, 상권 상세, 비교 | 실제 매물 연결, 사업계획서 작성, 신청 대행 |

> 💡 **배치 주기 분리 (권고)**
>
> 팀 문서는 세 표를 모두 주 1회 cron으로 채운다. 지원사업 공고는 수시로 바뀌므로 주 1회가 맞지만, 상권 · 인구 원천은 분기 단위로 갱신되므로 임대료표와 예측표를 매주 다시 만들어도 값이 바뀌지 않는다.
>
> cron은 주 1회로 두되, 상권 원천의 갱신 분기가 바뀌었을 때만 임대료표 · 예측표 · 요약 캐시를 재생성하도록 조건을 두는 것을 권한다. 학습 비용과 결과 변동을 줄일 수 있다.

### 3.4 저장소 구조

파이썬은 한 저장소에 모으고 프론트는 분리한다. 2026.09.26에 TownSignalBE를 TownSignalServer로 바꾸고 아래 구조로 교체했다(PR #4 머지 완료).

```
TownSignalServer/
├── api/          # FastAPI 동기식. DTO는 api/schemas/에만    ← common import
├── batch/        # 수집 · 전처리 · 학습 · 표 생성             ← common import
│   └── jobs/     #   python -m batch.jobs.<작업명> 으로 실행
├── common/       # evaluator · budget · scoring · constants   (Pydantic 없음)
├── data/         # raw · processed · seed   → 팀 「데이터 파이프라인」 페이지
├── tests/
├── Dockerfile          # api 이미지
├── Dockerfile.batch    # batch 이미지
└── docker-compose.yml

TownSignalFE/     # React SPA (별도 저장소)
```

| 디렉터리 | 역할 | 규칙 |
|---|---|---|
| common/ | 자격요건 평가(evaluator), 가용예산 계산(budget), 순위 점수(scoring), 상수 | 순수 파이썬 함수. 프레임워크(FastAPI · Pydantic · DB 세션)에 의존하지 않는다 |
| batch/ | 수집 · 전처리 · 임대료 추정 · 모델 학습 · 전 조합 예측 · 공고 구조화 · 요약 생성 | API로 노출하지 않는다. cron 또는 수동으로 실행한다 |
| api/ | 요청 검증, 서빙 표 조회, common 호출, 응답 조립, 인증 | 모델 파일을 로드하지 않는다. 요청 DTO는 api/schemas/에만 둔다 |
| data/ | 원천 · 가공 · 시드 데이터 | 대용량 원천은 저장소에 올리지 않고 내려받기 스크립트로 관리한다 |
| (별도 저장소) web | 화면 | 계산 로직을 두지 않는다. 표시만 담당한다 |

> 💡 **프론트를 합치지 않는 이유**
>
> common/을 공유해야 하는 것은 파이썬 쪽(api · batch)뿐이다. 프론트는 common을 쓰지 않는다.
>
> 툴체인(Node/Vite)과 배포 대상(Vercel)이 달라 한 저장소에 넣으면 CI에 경로 필터가 필요해진다. 분리해두면 서버 저장소는 전부 파이썬이라 테스트를 그냥 다 돌리면 된다.
>
> 프론트와 서버는 코드가 아니라 API 명세로만 엮이고, 프론트는 한 사람이 담당한다.

> 💡 **이미지를 둘로 나누는 이유**
>
> 예측을 요청 때 계산하지 않고 prediction 표에서 읽으므로 API 이미지에는 xgboost · scikit-survival이 필요 없다. Dockerfile(api)과 Dockerfile.batch를 분리해 API 이미지를 가볍게 유지한다.
>
> 배치는 python -m batch.jobs.<작업명> 형태로 EC2 cron이 실행한다. 의존성이 겹치지 않아 배포와 학습을 따로 다룰 수 있다.

### 4.2 동기식 FastAPI를 쓰는 이유

요청 경로가 DB 조회와 사칙연산만으로 끝나므로, 외부 API 대기를 겹쳐 처리해 이득을 보는 async의 장점이 발생하지 않는다. 동기식은 코드와 디버깅이 단순하고, 동기 스크립트인 배치와 common 모듈을 그대로 공유할 수 있다. FastAPI는 동기 핸들러(def)를 스레드 풀에서 실행하므로 동시 요청 처리에도 문제가 없다.

### 4.3 PostgreSQL을 쓰는 이유

| 항목 | PostgreSQL | MySQL |
|---|---|---|
| 분위수 집계 | percentile_cont로 중앙값 · 분위수를 한 번에 계산 | 중앙값 집계 함수가 없어 윈도우 함수로 우회 |
| 공간 데이터 | PostGIS 확장, GeoPandas read_postgis / to_postgis 직접 연동 | 공간 기능이 제한적이고 GeoPandas 직접 연동 없음 |
| 윈도우 함수 · CTE | 지원 | 8.0부터 지원 (차이 없음) |
| 전환 비용 | - | 초기 Spring 설정의 MySQL 드라이버는 2026.09.26 교체 때 함께 제거됨 |

임대료표는 공시지가를 행정동 단위로 집계해 만들므로 분위수 집계와 공간 결합을 반복한다. 엔티티와 스키마가 아직 없던 시점에 전환해 비용이 들지 않았다. 다만 실제 접속은 아직 붙이지 않았으므로(요청 경로에 DB 세션만 준비된 상태) 팀이 MySQL을 원하면 지금도 바꿀 수 있다.

## 5. AI 모델 설계

### 5.1 구성 개요

학습 모델은 두 개이고, 모두 배치에서만 실행된다. 요청 시에는 모델을 부르지 않고 예측표를 조회한다. 지원금 매칭은 학습 모델이 아니라 결정적 규칙 판정이다.

| 구성요소 | 종류 | 역할 | 실행 시점 |
|---|:---:|---|:---:|
| 모델 A | 회귀 | 행정동 × 업종의 점포당 분기 매출 예측 (구간) | 배치 |
| 모델 B | 생존 분석 | 행정동 × 업종의 1년 · 3년 생존 확률 예측 | 배치 |
| 지원금 매칭 | 규칙 판정 (학습 없음) | 인적 조건과 요건 비교, 금액 합산 | 요청 시 (common) |
| LLM ① | 언어 모델 | 지원사업 공고를 구조화된 데이터로 추출 | 배치 · 주 1회 |
| LLM ② | 언어 모델 | 행정동 상세 요약문 426건 사전 생성 | 배치 · 분기 1회 |
| 추천 결과 요약 | 템플릿 (LLM 미사용) | 계산값을 문장 틀에 채움 | 요청 시 (권고) |

### 5.2 모델 A — 점포당 분기 매출 (회귀)

#### 5.2.1 타깃 정의

> ⚠️ **예측 대상은 총매출이 아니라 점포당 매출이다**
>
> 원천(추정매출-행정동, OA-22175)의 매출은 행정동 × 업종 × 분기 단위로 합산된 총액이다. 이를 그대로 예측하면 점포가 많은 동네일수록 값이 커져 '가게 하나가 얼마 버는가'와 어긋나고, 순위에서 점포 밀집 지역이 무조건 1등이 된다.
>
> 타깃 = 분기 매출 금액 ÷ 점포 수 (점포-행정동, OA-22172와 같은 키로 결합). 팀 문서의 '예상 분기매출'도 이 정의로 명시한다.
>
> 화면에는 '이 지역 해당 업종의 점포당 평균 매출 추정치'로 표기하고 개별 점포 매출 보장이 아님을 함께 적는다.

#### 5.2.2 피처

| 구분 | 피처 | 출처 |
|---|---|---|
| 업종 · 지역 | 업종 코드, 자치구 코드, 행정동 코드 | 상권분석서비스 공통 코드 |
| 경쟁 환경 | 점포 수, 유사 업종 점포 수, 프랜차이즈 점포 수, 개업률, 폐업률 | 점포-행정동 (OA-22172) |
| 수요 | 길단위(유동)인구 총계와 연령 · 성별 · 시간대 분포 | 길단위인구-행정동 (OA-22178) |
| 구매력 | 소득 분위, 지출 총금액 | 소득소비-행정동 (OA-22166) |

#### 5.2.3 알고리즘

| 구분 | 알고리즘 | 역할 |
|---|---|---|
| 베이스라인 | 선형 회귀, RandomForest | 성능 하한선 확인 |
| 주력 | XGBoost Regressor | 정형 데이터에서 안정적 성능, 결측 · 범주 처리 용이 |
| 비교군 | MLP (PyTorch) | 계획서의 딥러닝 비교 요구. 동일 분할 · 동일 피처로 비교 |

#### 5.2.4 전처리

- 매출 분포가 한쪽으로 치우치므로 타깃에 로그 변환을 적용하고, 평가 지표는 원래 단위로 되돌려 보고한다.
- 점포 수가 기준 미만인 행정동 × 업종 조합은 학습에서 제외하고, 예측표에는 '데이터 부족' 플래그로 남긴다.
- 업종 코드는 범주가 많아 순서형 또는 타깃 인코딩을 쓴다. 타깃 인코딩은 학습 분할 안에서만 통계를 계산해 누수를 막는다.

#### 5.2.5 데이터 기간과 분할

> ⚠️ **2021년 이후 20개 분기, 2024년에 공간 기준 변경**
>
> 매출 · 유동인구는 2021년 이후 자료만 제공된다(약 20개 분기). 또한 2024년부터 공간 기준이 표준단위구역으로 바뀌어 2023년과 2024년 사이 값이 같은 기준으로 이어지지 않는다.
>
> 무작위 분할은 쓰지 않는다. 같은 행정동의 인접 분기가 학습과 테스트에 동시에 들어가면 성능이 과대평가된다.
>
> 분기 기준 시간 분할을 쓰고, 기준 변경 여부를 피처로 넣은 모델과 2024년 이후 분기만으로 학습한 모델을 비교해 채택한다. 분할 경계는 실제 확보 분기 수를 확인한 뒤 확정한다. (확인 필요)

#### 5.2.6 예측 구간

XGBoost의 분위수 목적함수로 하위 10% · 중앙값 · 상위 90% 모델을 각각 학습해 80% 구간을 만든다. 구간의 신뢰성은 테스트셋에서 실제값이 구간 안에 들어온 비율(포함률)로 검증한다.

#### 5.2.7 평가 지표

| 지표 | 목표 | 용도 |
|---|---|---|
| R² (결정계수) | 0.6 이상 | 계획서 목표. 설명력 확인 |
| MAE / MAPE | 참고 | 금액 오차 감각 확보, 화면 문구 근거 |
| 구간 포함률 | 80% 구간 기준 근접 | 구간 신뢰성 검증 |

### 5.3 모델 B — 생존 기간 (생존 분석)

#### 5.3.1 문제 정의

LOCALDATA 인허가의 개업일 · 폐업일로 점포의 영업 지속 기간을 모델링한다. 관측 시점까지 영업 중인 점포는 실제 영업 기간을 알 수 없으며(우측 절단), 이를 다루기 위해 일반 회귀가 아닌 생존 분석을 쓴다.

| 잘못된 접근 | 발생하는 문제 |
|---|---|
| 폐업한 점포만 학습 | 오래 버틴 점포가 빠져 생존 기간이 체계적으로 짧게 추정된다 |
| 영업 중 점포의 현재까지 기간을 정답으로 사용 | 끝나지 않은 기간을 최종값으로 간주해 역시 과소추정된다 |
| 영업 중 점포를 모두 제외 | 표본의 상당 부분이 사라지고 생존 편향이 남는다 |

#### 5.3.2 알고리즘

| 구분 | 알고리즘 | 특징 |
|---|---|---|
| 베이스라인 | Cox 비례위험 모형 (lifelines) | 계수로 폐업 위험 요인을 설명 가능. 비례위험 가정 검정 병행 |
| 주력 | Random Survival Forest, XGBoost AFT | 비선형 · 상호작용 포착. C-index로 베이스라인과 비교해 채택 |
| 선택 | DeepSurv (MLP 기반) | 여력이 있으면 딥러닝 비교군으로 추가 |

#### 5.3.3 피처와 관측 기간 제약

피처는 점포의 개업 분기 시점 행정동 · 업종 상권 지표를 쓴다. 폐업 이후 정보를 넣으면 미래 정보를 미리 보는 것이 되므로 개업 시점 값만 결합한다.

> ⚠️ **상권 피처가 2021년 이후에만 있다**
>
> 인허가 이력은 수십 년치가 있지만 결합할 상권 지표는 2021년 이후뿐이다. 따라서 학습 표본은 2021년 이후 개업 점포로 한정되고, 관측 기간은 최대 약 5년이다.
>
> 1년 · 3년 생존 확률까지는 추정할 수 있으나 그 이상은 외삽이 된다. 서비스 출력은 1년 · 3년 생존 확률로 두고, 중앙 생존 기간은 추정 가능한 조합에서만 표시한다. (확인 필요)

#### 5.3.4 평가와 출력

| 항목 | 내용 |
|---|---|
| 주 평가 지표 | Harrell C-index 0.7 이상 (계획서 목표) |
| 보조 지표 | 시간 의존 AUC, Brier score |
| 예측표 출력 | 행정동 × 업종별 1년 · 3년 생존 확률 |
| 화면 표기 | '이 지역 · 업종의 3년 생존 확률 추정치'로 표기, 개별 점포 보장 아님을 명시 |

### 5.4 성장세 지표

이미 확보한 매출 시계열에서 계산하는 파생 피처다. 행정동 × 업종별 점포당 매출의 1년 전 동일 분기 대비 증감률로, 현재 수치는 평범하지만 상승 중인 지역이 순위에 반영되게 한다.

```
growth(dong, category, q) =
    (per_store_sales[q] - per_store_sales[q-4]) / per_store_sales[q-4]

# q-4 = 1년 전 동일 분기 (계절성 상쇄)
# q와 q-4가 2023↔2024 공간 기준 경계를 넘으면 계산하지 않는다
#   → 경계 이후 분기끼리 비교 가능한 2025년 1분기부터 산출
# 표본이 적은 조합은 자치구 평균으로 대체하고 플래그를 남긴다
```

### 5.5 전 조합 일괄 예측과 예측표

학습이 끝나면 행정동 426 × 업종 100 = 42,600개 조합 전체를 한 번에 예측해 예측표에 적재한다. 요청 시에는 이 표를 조회만 한다.

| 컬럼 | 내용 |
|---|---|
| dong_code, category_code | 행정동 · 업종 키 |
| sales_p10, sales_p50, sales_p90 | 점포당 분기 매출 80% 구간과 중앙값 |
| survival_1y, survival_3y | 1년 · 3년 생존 확률 |
| growth_rate | 성장세 (산출 불가 시 null) |
| data_quality | 정상 / 표본 부족 / 추정 대체 플래그 |
| model_version, base_quarter | 모델 버전과 기준 분기 (결과 재현 · 추적용) |

### 5.6 LLM 사용 범위

LLM은 숫자를 만들지 않는다. 비정형 공고문을 정리하고, 계산된 결과를 문장으로 옮기는 일만 한다. 모든 LLM 호출은 배치에서 일어나며, 요청 경로에는 LLM 호출이 없다.

#### 5.6.1 LLM ① — 지원사업 공고 구조화 (배치 · 주 1회)

```
{
  "program_name": "청년창업 사업화 지원",
  "scope": "자치구",                // 중앙 | 서울시 | 자치구
  "district_code": "11620",         // 자치구 사업일 때만
  "min_age": 19, "max_age": 39,
  "career_max_years": 3,
  "cert_required": [],
  "amount_max": 5000000,
  "support_type": "보조금",          // 보조금 | 융자 | 현물(공간·교육)
  "selection_type": "경쟁",          // 자동 | 경쟁
  "duplicate_allowed": false,
  "apply_period": "2026-03-01~2026-03-31",
  "source_url": "https://...",
  "verified": false                 // 검수 전에는 매칭에 쓰지 않음
}
```

> ⚠️ **검수 통과분만 쓴다**
>
> 추출 결과를 그대로 쓰면 잘못된 금액이 사용자 예산에 그대로 들어간다. verified가 참인 항목만 매칭에 사용한다.
>
> 무작위 표본을 원문과 대조해 필드 단위 정확도를 측정한다. 이 수치가 계획서의 '지원사업 정보 추출 정확도' 목표에 해당한다.
>
> 출력은 JSON 스키마로 강제하고, 스키마를 벗어난 응답은 자동 재시도한다.

#### 5.6.2 LLM ② — 행정동 상세 요약 (배치 · 분기 1회)

상권 상세 화면에 쓰는 요약문을 행정동 426건에 대해 미리 생성해 summary_cache에 적재한다. 요약 대상 수치(업종 분포, 초기비용, 최근 매출 추이)는 모두 배치 시점에 확정되어 있으므로 사전 생성이 가능하고, 요청 시에는 조회만 한다.

#### 5.6.3 추천 결과 요약 — 템플릿 (권고)

> 💡 **요청 시 LLM을 호출하지 않는 이유**
>
> 팀 문서의 요청 흐름 5단계는 'LLM 요약'을 포함하지만, LLM 호출은 보통 수 초가 걸려 1초 원칙과 충돌한다. summary_cache는 같은 요청이 두 번째 올 때부터만 도움이 된다.
>
> 추천 요약은 사용자마다 예산 · 지원금 맥락이 달라 미리 만들어둘 수도 없다(계획서 차별점 3번).
>
> 따라서 추천 결과 요약은 계산값을 문장 틀에 채우는 템플릿으로 만들고, LLM은 사전 생성이 가능한 행정동 상세 요약에만 쓰는 것을 권한다.

```
[템플릿 예]
{dong}은 {scenario} 예산 대비 {room}원 여유가 있습니다.
점포당 분기 매출은 {p10}~{p90}원(중앙 {p50}원), 3년 생존 확률은 {surv3}%입니다.
{if needs_selection}  이 결과는 {program} 선정을 전제로 합니다.
{if growth > 0}       최근 1년 매출이 {growth}% 늘었습니다.
```

#### 5.6.4 LLM 선택지

| 구분 | 외부 API (상용) | 로컬 실행 (Qwen 등) |
|---|---|---|
| 비용 | 토큰당 과금 | 없음 (자체 자원) |
| 품질 | 복잡한 공고문 추출에 유리 | 요약에는 충분, 추출 정확도는 낮을 수 있음 |
| 권장 용도 | LLM ① 공고 구조화 (정확도 우선, 배치라 시간 여유) | LLM ② 행정동 요약 (반복적, 비용 민감) |

### 5.7 딥러닝을 주력으로 두지 않는 이유

- 데이터가 정형 표이고 규모가 수만 행 수준이다. 이 조건에서는 트리 앙상블이 심층 신경망보다 안정적인 성능을 내는 것이 일반적이다.
- 추천 근거를 항목별로 설명해야 하므로 기여도 해석이 쉬운 모델이 유리하다.
- 계획서의 딥러닝 비교 요구는 동일 분할 · 동일 피처로 MLP를 학습해 수치로 비교하는 실험으로 충족한다.

### 5.8 성능 목표와 검증

| 항목 | 목표 | 검증 방법 |
|---|---|---|
| 매출 예측 정확도 | 테스트셋 R² 0.6 이상 | 시간 분할 테스트셋, 원 단위 환산 후 측정 |

### 6.3 행정동 임대료 추정

임대료표는 행정동 426행에 대해 보증금 · 월세 · 초기비용 추정치를 담는다. 계획서의 원천이 종료되어 다른 경로가 필요하다.

| 검토한 방법 | 결과 |
|---|---|
| 부동산원 상가 임대료 단독 사용 | 소규모상가 표본이 전국 5,526동 · 232개 상권뿐이라 행정동 단위로 내려갈 수 없다 |
| 상권 지표로 임대료를 회귀 추정 | 임대료가 매출 · 생존 모델의 피처로도 쓰여 순환 참조가 된다 (팀 v0.3에서 불가 판정) |
| 개별공시지가 + 부동산원 단가 결합 (채택) | 공시지가는 전 필지를 덮으므로 행정동 해상도가 나온다. 금액 수준은 부동산원 단가로 맞춘다 |

```
1. 용도지역으로 상업 · 근린 용도 필지만 남긴다
2. 행정동별 공시지가 중앙값 → 서울 전체 대비 상대지수
3. 상대지수 × 해당 상권 또는 자치구의 부동산원 상가 임대 단가 → 행정동 추정 월세 · 보증금
4. 초기비용 = 보증금 + 월세 × 예비 개월수 + 업종 평균 시설비   (가정 · 7.4절)
```

세부 계산과 검증 기준은 팀 「데이터 파이프라인」 페이지의 2순위 임대료 경로를 따른다. 추정치이므로 화면에는 '추정 임대료'로 표기한다.

### 6.4 행정동 단위 통일

| 원천 단위 | 변환 방법 | 주의 |
|---|---|---|

### 6.6 데이터 품질 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 임대료 원천 종료 | 초기비용을 계산할 수 없어 예산 필터 전체가 막힘 | 공시지가 + 부동산원 단가 결합 추정 (6.3절). 가장 먼저 끝내야 함 |
| 2024년 공간 기준 변경 | 시계열 단절로 성장세 · 학습이 왜곡 | 경계 표시 컬럼, 경계를 넘는 성장세 계산 금지, 비교 학습 |

### 7.2 2단계 API 흐름

추천은 두 번의 요청으로 나뉜다. 먼저 가용 예산을 보여주고, 사용자가 확인한 뒤 추천을 받는다. 가용 예산 화면을 별도로 두는 것은 팀 문서가 지적한 '명세서에 빠진 화면'을 채우는 역할도 한다.

| 단계 | API | 입력 | 처리 | 출력 |
|:---:|---|---|---|---|
| 1 | calculate-budgets | 나이 · 자격증 · 경력 · 자본금 · 업종 | common/evaluator로 지원사업 판정 → common/budget로 자치구별 합산 | 자치구 25개별 보수 · 기대 예산, 매칭된 사업 목록 |
| 2 | recommendations | 1단계 조건 + 선택 자치구(선택) | district_rent로 여유 계산 → prediction 조회 → common/scoring으로 순위 | 추천 행정동 순위, 항목별 근거, 템플릿 요약 |

### 7.3 가용 예산 — 보수와 기대 (권고)

> ⚠️ **'받을 수 있는 금액'이 부풀려지지 않게 한다**
>
> 창업 지원사업의 상당수는 요건만 맞으면 받는 돈이 아니라 경쟁을 거쳐 선정된다(예: 청년창업사관학교). 자격 충족을 곧 수령으로 계산하면 가용 예산이 실제보다 커진다.
>
> 융자는 갚아야 하는 돈이고, 공간 · 교육 지원은 현금이 아니다. 이들을 보조금과 같은 '금액'으로 더하면 안 된다.
>
> 보수 예산 = 자본금 + (자동 지급 · 보조금). 기대 예산 = 보수 + (경쟁 선정 · 보조금). 융자는 별도 표시, 현물 지원은 초기비용 차감 항목으로 처리한다.
>
> 필터는 기대 예산으로 하고, 각 추천 행정동에 보수 예산 기준 통과 여부를 함께 표시한다. 차별점(지원금이 선택지를 넓힌다)은 살리면서, 어떤 결과가 선정을 전제로 하는지 사용자가 알 수 있게 한다.

```
보수[gu] = 자본금 + Σ amount_max   (자격 충족 ∧ selection=자동 ∧ type=보조금 ∧ 해당 구 적용)
기대[gu] = 보수[gu] + Σ amount_max (자격 충족 ∧ selection=경쟁 ∧ type=보조금 ∧ 해당 구 적용)
중복 수혜 불가 사업끼리는 금액이 큰 쪽만 합산
```

### 7.4 예산 필터

```
여유[dong] = 기대[gu(dong)] - initial_cost[dong]        # gu(dong) = dong_code 앞 5자리
통과 조건 : 여유[dong] >= 0
보수 통과 : 보수[gu(dong)] - initial_cost[dong] >= 0    # 결과 배지로 표시

initial_cost = deposit + monthly_rent × 예비개월(기본 6) + 업종 평균 시설비   (가정)
```

초기비용에 무엇을 넣는지에 따라 통과 지역이 크게 달라진다. 예비 개월수와 업종 평균 시설비의 근거 자료를 확보해 확정해야 한다. (확인 필요)

### 7.5 순위 산정

```
score = w1 · norm(sales_p50)        # 점포당 분기 매출 중앙값
      + w2 · norm(survival_3y)      # 3년 생존 확률
      + w3 · norm(여유율)            # 여유 / 기대 예산
      + w4 · norm(growth_rate)      # 성장세 (null이면 0으로 두고 가중치 재분배)

norm() : 통과 후보 집합 안에서 min-max 정규화
초기 가중치 (가정) : w1=0.35, w2=0.30, w3=0.20, w4=0.15
근거 분해         : 각 항의 (가중치 × 정규화값)을 화면에 그대로 표시
```

점수 계산은 common/scoring에 두어 배치에서 사전 검증할 때와 요청 시에 같은 식을 쓴다.

### 7.6 응답 시간 (목표 1초)

| 단계 | 예산 | 근거 |
|---|---|---|
| 지원사업 판정 · 예산 합산 | 100ms 이내 | 수백 행 조회 + 비교 연산 |
| 임대료 조회 · 여유 계산 | 100ms 이내 | 426행 조회 + 뺄셈 |
| 예측표 조회 | 200ms 이내 | 통과 행정동 × 희망 업종, (dong_code, category_code) 인덱스 |
| 정렬 · 근거 분해 · 템플릿 요약 | 100ms 이내 | 메모리 연산 |
| 여유 | 약 500ms | 네트워크 · 직렬화 · 인증 |

### 7.7 예외 처리

| 상황 | 처리 |
|---|---|
| 매칭되는 지원사업이 없음 | 자본금만으로 계산하고 그 사실을 화면에 명시 |
| 통과하는 행정동이 없음 | 여유가 가장 작은 음수인 지역부터 차선 후보로 제시하고 부족 금액을 안내 |
| 예측 표본 부족 조합 | 순위에서 제외하고 '데이터 부족' 사유 표시 |
| 요약 캐시 없음 | 상세 화면에서 요약 영역을 숨기고 지표만 표시 |
| 배치 실패 | 직전 표를 유지하고 기준 분기를 화면에 표시. 부분 갱신을 막기 위해 표 교체는 트랜잭션으로 수행 |

### 7.8 보조 흐름

- 직접 찾아보기: 조건 없이 자치구 · 행정동을 검색해 상권 상세로 이동한다.
- 상권 상세: 업종 분포, 추정 임대료, 매출 추이, 예측 구간, 요약 캐시의 요약문을 보여준다.
- 상권 비교: 2~3개 행정동을 같은 축으로 나란히 비교한다.
- 대시보드: 로그인 사용자의 최근 추천과 즐겨찾기를 보여준다.

## 10. 배포 및 인프라

### 10.1 환경 구성

| 구성 요소 | 로컬 개발 | 운영 |
|---|---|---|
| DB | docker-compose의 PostgreSQL 컨테이너 | RDS 또는 EC2 내 컨테이너 (확인 필요) |
| API | docker-compose의 api 컨테이너 | ECR 이미지 → EC2 컨테이너 |
| 웹 | docker-compose의 web (Vite 개발 서버) | Vercel 정적 배포 |
| 배치 | docker compose run batch ... | EC2 cron이 배치 컨테이너 실행 |
| 모델 파일 | 배치 내부에서만 사용 | API 이미지에 포함하지 않음 (예측표만 조회) |

### 10.2 CI/CD

- CI: PR과 push 시 common · api · batch 테스트와 린트를 실행한다. common은 배치와 API 양쪽이 쓰므로 테스트 우선순위가 가장 높다.
- 배포: 초기에는 수동 실행으로 두고, 인프라 · 시크릿 구성이 끝나면 main push 시 자동 배포로 전환한다.
- 이미지 태그를 버전으로 관리해 실패 시 이전 이미지로 되돌린다.

### 10.3 파이프라인 전환 결과 (2026.09.26 완료)

| 항목 | 이전 (Spring) | 현재 (FastAPI) |
|---|---|---|
| Dockerfile | JRE 이미지 + jar 실행 | python 슬림 + uvicorn (api) / 학습 의존성 포함 별도 이미지 (batch) |
| CI | JDK 21 + Gradle build | Python 3.11 + ruff + pytest |
| 설정 주입 | application-*.yml을 시크릿에서 복원 | 환경변수 주입, .env는 저장소에 두지 않음 |
| 이미지 태그 | latest | latest + 커밋 SHA (롤백용) |
| 포트 | 8080 | 8000 |
| 유지 | ECR 인증, EC2 IAM Role, 시크릿, PR 라벨링 | 그대로 재사용 |

CI는 배치 의존성(xgboost · scikit-survival)을 설치하지 않는다. 설치가 무거워 common과 api 테스트만 돌리며, 배치 작업이 붙으면 별도 job으로 분리한다. 도커 이미지 빌드는 아직 로컬에서 확인하지 못했다. (확인 필요)

### 10.4 설정과 비밀 관리

- DB 접속 정보, JWT 서명 키, LLM API 키, 공공데이터 인증키는 저장소에 두지 않고 GitHub Secrets → 환경변수로 주입한다.
- LLM 키는 배치에서만 필요하므로 API 컨테이너에는 주입하지 않는다.
- CORS 허용 도메인은 Vercel 배포 주소가 확정되면 설정한다.

> ⚠️ **유일한 구조적 위험 — 데이터 통합 대기**
>
> 데이터 통합이 끝날 때까지 나머지 넷이 기다리는 것이 가장 큰 위험이다. 지원사업표는 상권 데이터와 무관하므로 대기 인력을 그쪽에 붙이면 병목이 풀린다.
>
> 지원사업 구조화는 경쟁 서비스 어디에도 없는 부분이라 차별점도 여기에 있다.

### 11.2 우선순위

| 순위 | 범위 | 판단 기준 |
|---|---|---|
| 1순위 (필수) | 지원금 매칭 · 가용 예산, 임대료표 · 예산 필터, 생존 예측, 상권 상세, 추천 화면 | 이것만으로 역산 흐름이 끝까지 동작한다 |
| 2순위 (목표) | 매출 예측, 성장세, 행정동 요약(LLM ②), 비교, 대시보드 · 즐겨찾기 | 완성도를 높이지만 없어도 흐름은 성립한다 |
| 3순위 (도전) | 예측 구간 고도화, 매칭 정교화, 민원 텍스트 보정 | 여력이 있을 때 착수 |

매출 예측이 늦어지면 순위는 생존 확률 · 여유율 · 성장세만으로 산정하는 축소 방식을 임시로 쓴다.
